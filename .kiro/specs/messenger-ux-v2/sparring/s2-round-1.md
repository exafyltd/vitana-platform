Session: `523b58d3-8841-478b-921e-d7b575396eec` · plan hash `aa2751a8c5211286f8cdfececbcf4a36a733808d6632e92417477f36553117e3`

## Summary

The plan is largely well-researched and its platform-side premises about the chat schema, push dispatch, and notification pipeline are accurate. However, I found one blocker (viewing-presence flow does not actually suppress pushes end-to-end because the recipient-viewing heartbeat posts `active:true` as the VIEWER and the suppression check keys on the RECIPIENT, but the critical issue is that `notifyUser` is never modified and it doesn't get the recipient's viewing state — the design injects the check inside `notifyUser` but the lane's own declared file list shows `notification-service.ts` is edited, and the suppression requires matching the viewer's `dm:<peerId>` to the sender-derived `dm:<sender_id>`, which are different users) plus a serious correctness issue with the `chatConversationKeyFromData` fallback chain, and several major gaps around reply security, duplicate suppression races, and the "new_group_message" data.type divergence. Testing/validation goes missing for the reply path (reply_to_message_id exposure is asserted but no read-side trust boundary is specified for forged RLS inserts).

## Findings

### R1-F1 [blocker]

The viewing-presence suppression key mismatch means the check will suppress the wrong conversation or never match, defeating R13. `chatConversationKeyFromData(data)` derives the key as `dm:<sender_id>` (from the push payload's `sender_id`), but the viewing-presence row is written by the VIEWER with key `dm:<peerId>` where peerId is the OTHER user (the sender). For a DM from A→B, the push to B carries `sender_id = A` so the suppression check computed `dm:<A>`, but B's heartbeat posted `active:true` for `dm:<A>` only if B has the conversation with A open — which is correct ONLY because `peerId` in B's client is A. However there is no place where the recipient's open-conversation key is matched against `sender_id`, because the plan's own `chatConversationKeyFromData` uses `sender_id` (the message sender) while I4's `POST /chat/viewing` uses `dm:<peerId>` where peerId is the person being viewed. For group messages the push data has `group_id` so the group key matches. For DMs, the sender_id-as-key is coincidentally equal to the peer B is viewing, so DMs match; but this equivalence is NOT established or verified anywhere and the plan never states that the recipient's `dm:<peerId>` equals the push's `sender_id` — and it breaks the moment a user has a DM conversation open with a DIFFERENT peer than the sender (no match, correct) vs the intended case. The two candidate checks (`notifyUser` and `/push-dispatch`) both rely on `chatConversationKeyFromData`, and neither is shown to receive the RECIPIENT's own viewing key. The fundamental gap: nothing in the plan connects the recipient's presence row to the recipient's own viewer perspective — `chat_viewing_presence.user_id` is the viewer, and the check must match `user_id = recipient` AND `conversation_key = <what the recipient sees>`, but `chatConversationKeyFromData` produces a sender-centric key.

Suggestion: Define the presence key from the RECIPIENT's perspective and make the check explicit: presence key for a DM is `dm:<sender_id>` where sender_id is the OTHER party as seen by the viewer, i.e. the recipient of a push from A stores `dm:<A>` (peerId=A). ### R1-F2 [blocker]

The plan does not modify any push caller and injects the viewing check inside `notifyUser`, but `notifyUser` receives the push payload `data` as an argument and the recipient as `userId`. For greeting DMs (new-member-greeting-push) and orb-tools voice sends, the payload `data.conversation_key` is set from `chatConversationKey({ senderId })` = `dm:<sender>`, and `data.sender_id` IS present, so the DM key resolves. But the plan's `chatConversationKeyFromData` priority order is `data.conversation_key` FIRST. For greeting DMs the greeting push payload sets `conversation_key` (line 147) AND later the same `data` carries `GREETING_GROUP_KEY`. This is consistent. The real blocker is elsewhere: the plan declares the check lives in a new `services/chat-viewing-presence.ts` called from `notifyUser` and `/push-dispatch`, but ALSO declares 'No push caller is edited' and '`NotifyUserOptions` is unchanged'. Every push to a recipient MUST be suppressed when that recipient is viewing — but `notifyUser` is called with only `userId, tenantId, type, payload, supabase, opts` and has NO access to whether that specific (recipient, conversation) is viewing unless it performs the presence read itself. The plan says it does perform the read inside `notifyUser` for `type ∈ {new_chat_message, chat_mention}`. That is workable, but the plan's OWN scope statement in lane 2 says `notification-service.ts` is edited — contradicting 'No push caller is edited' only if callers are distinct from notification-service (they are). This is not itself a blocker. Re-classified: the genuinely blocking defect is F1 (key-mismatch). This finding documents the secondary risk that greeting/voice/calendar `data` variants that set only `sender_id` (no `conversation_key`) resolve correctly ONLY via the `sender_id` fallback, which is not enumerated as tested.

### R1-F3 [major]

The reply security model relies on `reply_to_message_id` being validated as same-conversation at SEND time, but the read-side trust boundary is underspecified and the plan's claim that forged RLS inserts show 'original message not available' ignores that `metadata.reply_to = {message_id}` can be forged by any user with INSERT rights via the existing `users_send_messages` RLS policy (WITH CHECK auth.uid() = sender_id, no check on metadata.reply_to). A malicious/buggy client can set `metadata.reply_to = {message_id: <some other user's DM id>}` and the read endpoint resolves the quote from 'that conversation's rows or I3' — but if the target message is in the SAME conversation (e.g. the sender's own prior DM), it's fine; the risk is if the forged id points to a message in a DIFFERENT conversation and I3 returns 404 (so 'not available'), which is safe. However the plan never specifies that the READ endpoint re-validates `reply_to_message_id` against the conversation, only that I3 404s outside it — I3's `around` 404s when the target is not in that conversation, but the reply QUOTE resolution is a separate path in the client (`ConversationView` resolves parent from loaded rows, not via I3). The plan asserts the client 'trusts it only inside the same conversation' by resolving via I3 which 404s outside, but the DM/group read endpoints expose `reply_to_message_id` from `metadata.reply_to` WITHOUT server-side conversation membership validation, and the current gateway `insertChatMessage` does no `metadata` validation at all.

- `exafyltd/vitana-platform:supabase/migrations/20260225200000_chat_messages.sql:23` — CREATE POLICY "users_send_messages" ON chat_messages FOR INSERT WITH CHECK (auth.uid() = sender_id);
- `exafyltd/vitana-platform:services/gateway/src/routes/chat-repository.ts:20` — export async function insertChatMessage(sb: SupabaseClient, row: Record<string, unknown>) {
  return sb.from('chat_messages').insert(row).select().single();

Suggestion: Specify that the read endpoints (or a shared resolver) validate `metadata.reply_to.message_id` as belonging to the same conversation (same DM pair / same group) before exposing `reply_to_message_id`, returning the id ONLY for in-conversation targets and null otherwise — do not depend solely on I3's `around` 404, since the client's reply-quote path (parent resolved from loaded rows) does not go through I3. Add a test asserting a forged cross-conversation `metadata.reply_to` is not exposed/misrendered.

### R1-F4 [major]

The duplicate-row defense ('suppressed_duplicate') has a race: `/push-dispatch` marks an unpushed chat row `suppressed_duplicate` when another row of the same user_id and `data->>'message_id'` already has `push_sent_at`, and `notifyUser` does the symmetric check before writing. Both run concurrently at the gateway, but the vitana-v1 trigger `notify_on_chat_message`/second-writer row is written by a DB INSERT trigger with `push_sent_at NULL`, and the plan's own measured note says 'the trigger's insert does not land today' and 'live body differs from the repo's last migration — drift recorded'. The two defensive rules (a) and (b) are not sufficient: rule (a) in `/push-dispatch` only marks rows whose sibling ALREADY has push_sent_at, but if both rows are NULL and picked in the SAME cron batch (or two overlapping cron ticks), neither sees the other as pushed and BOTH can push. There is no locking/transactional guard, and `fetchPendingPushNotifications` returns up to 100 rows with no per-user ordering guarantee that would make the duplicate rows adjacent.

- `exafyltd/vitana-platform:services/gateway/src/routes/scheduled-notifications-repository.ts:221` — return sb.from('user_notifications').select('id, user_id, tenant_id, type, title, body, data, channel, priority, created_at').is('push_sent_at', null).in('channel', ['push', 'push_and_inapp']).gte('created_at', lookbackCutoff).order('created_at', { ascending: true }).limit(100);

Suggestion: Make the duplicate suppression order-independent: within a single cron batch, resolve all unpushed chat rows' `message_id`s first (the plan already does one batched sender/group lookup for presence), then for any two rows of the same (user_id, message_id) in the batch, mark all but one `suppressed_duplicate` BEFORE any push is sent. Also document that the trigger not being changed means a re-enabled/updated trigger could reintroduce duplicates, and add a test for the both-NULL simultaneous case.

### R1-F6 [major]

I2 delivery/read propagation: the plan states `/chat/read` sets `delivered_at` when NULL, and senders 'observe both through realtime UPDATE on chat_messages (`sender_id=eq.<me>`)'. But the existing `markPeerMessagesRead` in the repository updates by `.eq('sender_id', peerId).eq('receiver_id', userId)` — it updates rows where the CALLER is the receiver, and the realtime UPDATE RLS for the SENDER relies on the sender being able to SELECT rows where `sender_id = auth.uid()`. The plan's I2 requires senders to see `delivered_at`/`read_at` on their OWN sent DMs via realtime UPDATE, which requires the UPDATE RLS policy (`users_mark_received_read`, USING auth.uid() = receiver_id) to permit the SENDER to observe changes — it does not: the sender can only SELECT (users_read_own_messages), and realtime UPDATE events are gated by the SELECT policy, so the sender CAN see updates to their own sent rows (sender_id = me passes users_read_own_messages SELECT). That part holds. The gap is that I2 requires a NEW realtime filter `sender_id=eq.<me>` and the plan asserts 'existing SELECT RLS' covers it — but for GROUP messages, the plan says groups have NO delivered/read state, so the sender never advances past Sent. This is stated, but the client I7 says group messages 'stop at sent' — consistent. No blocker, but the realtime UPDATE subscription for `delivered_at`/`read_at` on own DMs is a new subscription surface with a new filter not tested for the `users_read_own_messages` policy covering UPDATE events in Supabase Realtime (which uses the SELECT policy for the *updated* row); this should be verified, not asserted.

Suggestion: Add an explicit test/verification that a sender's realtime UPDATE subscription filtered `sender_id=eq.<me>` delivers `delivered_at`/`read_at` changes under the existing `users_read_own_messages` SELECT policy, and that the `/chat/delivered` route's `receiver_id = caller` guard cannot mark another user's row (the plan lists this as a key case — keep it, but also test the realtime delivery side).
