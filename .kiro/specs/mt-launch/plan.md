# mt-launch — Tenant Launch engineering (WS8): pack intake, content pipeline, tenant-owner analytics, support & landing

<!-- plan:begin -->
## Problem
WS8 engineering (MULTI-TENANT-PLAN.md §6 WS8) is the M2 "a new tenant launches" machinery. Verified today (read-only, 2026-10-15):

1. **Tenant pack intake has no data model.** A tenant's brand/content pack lives only as columns written through `provision_tenant()` and the admin API — `admin-tenants.ts` PACK_FIELDS = `display_name, brand, legal_entity_line, support_email, sender_name, sender_email, default_locale, enabled_locales, timezone, currency, landing, persona_facts` (`services/gateway/src/routes/admin-tenants.ts:383`). There is no record of what intake is still outstanding for a tenant (anchor-person consent, brand kit, Season 0 approval, calendar, seed groups, founding invites, revenue share, health-claims sign-off) — the readiness endpoint (`admin-tenants.ts:536`) only checks the provisioned columns.
2. **No AI-assisted content pipeline.** Nothing generates per-tenant content from Maxina templates, lints it (health claims, leftover `Maxina`/`Mariia` strings, undated time-bound claims), tracks review/sign-off, or publishes to overrides. The publish target `tenant_content_overrides(tenant_id, locale, key, value)` is designed by WS5 but **does not exist yet** (grep of `supabase/migrations/**` = 0). Health-claim discipline exists only as free-text prompt rules (`services/gateway/src/services/community-autopilot/drafts.ts:94`, `anthropic-vision-client.ts:68`), never a linter.
3. **Analytics is member/admin-facing, not tenant-owner-facing, and has no health lineage guard.** `product_analytics_events` (`supabase/migrations/20260612140000_BOOTSTRAP_product_analytics_events.sql:18`, tenant-scoped, service-role-only RLS) + daily rollups (`20260612140100…`) back `GET /api/v1/admin/tenants/:tenantId/analytics` (`routes/tenant-admin/product-analytics.ts`, `requireTenantAdmin`). There is no tenant-OWNER funnel (signups, activation, journey, events, retention) and **no lint stopping an owner surface from reading a health table** (D18). The guard pattern exists for commerce/matching — `test/vtid-05025-commerce-health-boundary.test.ts` and `test/vtid-05156-people-match-health-boundary.test.ts` scan source for a `HEALTH_TABLES` regex — but no analytics-surface equivalent.
4. **Support routing is not per-tenant.** `feedback_tickets` tickets route to platform specialists (Devon/Sage/Atlas/Mira, `live-tool-catalog.ts:1006`); the tenant-scoped read exists (`routes/feedback-admin.ts:231` `GET /tenants/:tenantId/tickets`) but there is no per-tenant answerer / SLA / support contact resolution.
5. **Landing SEO/OG/referral attribution is single-tenant in shape.** Referral/invite attribution already works and is tenant-scoped (`referrals`, `sharing_links`, `signup_attempts.referral_code`, `routes/community-invites.ts:79`, `routes/admin-signups.ts:208-229`), but SEO/OG metadata is Maxina-shaped (OG assets via `tenants` `og_image`, `admin-tenants.ts:471`) and there is no per-tenant landing SEO/OG/referral-invite attribution surface a launching tenant configures.

## Fix (per lane)
- **`pack-intake-db` (DB, repo vitana-platform).** New table `tenant_pack_intake(tenant_id FK tenants, item_key, status, evidence jsonb, decided_by, decided_at, updated_at)` keyed `(tenant_id, item_key)`; `item_key` enumerates the WS8 intake checklist (identity+anchor-person-consent, brand_kit, copy, persona_facts, brand_kb_docs, season0_approval, events_calendar_90d, seed_groups, host_moderator_support_sla, founding_invites_30, revenue_share, locales, health_claims_signoff). `status IN ('not_started','in_progress','blocked','approved')`. New table `tenant_content_pipeline(tenant_id, locale, key, source_template, candidate_value, lint_report jsonb, review_state, reviewed_by, signed_off_by, published_at)` with `review_state IN ('generated','linted','in_review','signed_off','published','rejected')`. Service-role-only RLS (gateway-mediated, like `product_analytics_events`). Migration version in this spec's range (§Migrations). Expand-only, no backfill. A read-only `get_tenant_launch_readiness(p_tenant_id)` SQL function returns intake completeness for the owner analytics + readiness surfaces.
- **`pack-intake-admin` (gateway code, repo vitana-platform).** `POST/GET/PATCH /api/v1/admin/tenants/:tenantId/pack-intake` (exafy_admin + tenant-admin per item sensitivity) over `tenant_pack_intake`; the AI-assisted content pipeline: `generateCandidate` (from Maxina templates), three **linters** run server-side as pure functions — `healthClaimLinter`, `leftoverBrandLinter` (flags `Maxina`/`Mariia` case-insensitive outside allowlisted immutable identifiers), `undatedClaimLinter` (flags time-bound claims with no date) — writing `lint_report`; review/sign-off state machine (`generated→linted→in_review→signed_off→published`, `→rejected`); **publish writes to `tenant_content_overrides`** (WS5's table; see Depends on) only from `signed_off`, then i18n seed. This lane also **creates the per-tenant dark-flag resolver** `services/tenant-launch/tenant-feature-flag.ts` — `isTenantFeatureLive(tenantId, 'mt.launch_*')` reads `tenant_settings.feature_flags.mt.launch_*` strictly `=== true`, default OFF, lookup error ⇒ off, cached, modelled on `services/data-export-consent.ts:79-108` + `data-export-consent-repository.ts:25`. This is NOT `isFeatureLive` (`feature-flags.ts:81`), which is single-arg and reads a GLOBAL env flag — it has no `tenantId` and cannot express a per-tenant dark flag. The pipeline is gated by `isTenantFeatureLive(tenantId, 'mt.launch_pipeline')`. Health-claim and leftover-brand linters block publish on any finding; `undatedClaimLinter` warns.
- **`tenant-owner-analytics` (gateway code, repo vitana-platform).** `GET /api/v1/admin/tenants/:tenantId/owner-analytics/{signups,activation,journey,events,retention}` reading `product_analytics_events`/rollups + `get_tenant_launch_readiness`, tenant-scoped via `requireTenantAdmin` + the tenant path segment (never a body/header tenant). **D18 lineage guard:** a build-failing source-scan test modelled on `test/vtid-05025-commerce-health-boundary.test.ts` asserts no owner-analytics module imports or `.from()`s any `health_*`/`wearable_*`/`biomarker_*`/`lab_*`/`vitana_index_*` table; **unknown-provenance data counts as health** (deny-by-default: the test allowlists the exact non-health tables these modules may read, anything else fails). Dark behind `isTenantFeatureLive(tenantId, 'mt.launch_analytics')` (the `tenant-feature-flag.ts` resolver `pack-intake-admin` creates — this lane imports it, hence `depends_on` it).
- **`support-landing` (gateway code, repo vitana-platform).** Per-tenant support routing: resolve the answerer + SLA + support contact from `tenants.support_email`/`sender_*` and a new `tenant_settings.feature_flags.mt.support` block, applied where `feedback_tickets` are created/triaged (`routes/feedback-admin.ts`, `routes/feedback-intake.ts`) so a tenant's tickets carry its support routing; landing SEO/OG per tenant from the brand pack (`tenants.landing`/`og_image`) exposed through the public registry read path; referral-invite **attribution stays as-is** (already tenant-scoped) — this lane only ensures the launching tenant's landing config and support contact are surfaced, no change to crediting logic. Dark behind `isTenantFeatureLive(tenantId, 'mt.launch_support')` (same resolver, imported from `pack-intake-admin`, hence `depends_on` it).
- **`worker-test-gate` (governance, executor claude, repo vitana-platform).** Wire the three linter unit suites, the D18 analytics lineage guard test, and the Maxina golden suite (unchanged assertion) into PR-GATE / the gateway Jest job so WS8 code cannot merge without them. Governance paths (`.github/workflows/**`) → executor claude.

## Tests
- Vitest/Jest (gateway): the three linters as pure functions (health-claim finding blocks publish; `Maxina`/`Mariia` detected and the immutable-identifier allowlist passes; undated time-bound claim warns); the pack-intake and pipeline route handlers (auth gates: non-admin 403, tenant isolation — a tenant-admin of T_B gets 403/empty for T_A); owner-analytics handlers (tenant-scoped, no health read); publish state machine refuses to publish from a non-`signed_off` state and writes to `tenant_content_overrides`.
- Source-scan guard test (D18): `test/mt-launch-owner-analytics-health-boundary.test.ts` — the owner-analytics modules match no `HEALTH_TABLES` regex and import no health repository; a self-test asserts the regex catches a planted read. Unknown-provenance tables are not on the read allowlist (fail-closed).
- pgTAP: `tenant_pack_intake`/`tenant_content_pipeline` reject a client (non-service-role) read; `get_tenant_launch_readiness` is read-only.
- Golden (rule from §6 WS0): the Maxina golden suite is unchanged by this spec (no persona/greeting/push/What's New change here); `npm run test:support` (rule 42c) stays green because support routing adds per-tenant resolution without changing the pipeline contract — any contract change adds a scenario in the same PR.
- `worker-test-gate`: PR-GATE runs the above; the gate itself has a check that the suites are referenced.

## Rollout
Every code lane is dark by default behind its own per-tenant flag (`mt.launch_pipeline`, `mt.launch_analytics`, `mt.launch_support`) under `tenant_settings.feature_flags`, resolved by this spec's `isTenantFeatureLive(tenantId, …)` (see Fix: `pack-intake-admin`), because PUBLISH promotes the whole staging build. These three per-lane flags are each independently default-OFF and stand entirely on their own. The program-wide master switch `MT_RESOLUTION_V2` does **NOT exist in the gateway today** (verified read-only 2026-10-15: case-sensitive grep of `services/gateway/**/*.ts` = 0 matches) — it is **mt-identity**'s (WS1) resolution switch to introduce, so this spec depends on mt-identity for it (see Depends on) but never defines or assumes it as an existing fact; the lanes are dark-safe without it. DB migrations applied by Claude via RUN-MIGRATION after merge, in MIGRATION-QUEUE order, after WS5's `tenant_content_overrides`. Owner-only / out-of-engineering ops steps (anchor-person consent, Season 0 approval, Exafy content sign-off, revenue-share agreement, founding-invite send, actually opening the tenant) are tracked as `tenant_pack_intake` items but performed by the owner/ops, not by code (see Out of scope). No Gate 2 for the DB-only or docs parts; code lanes follow merge → staging → STAGING-VERIFY → Gate 2 → PUBLISH.

## Risks
- Publishing generated content to `tenant_content_overrides` could surface un-reviewed strings. Mitigation: publish only from `signed_off`; health-claim and leftover-brand linters hard-block; dark flag; exafy_admin sign-off required.
- D18 leak: an owner-analytics query joining a health table. Mitigation: fail-closed source-scan allowlist (unknown table = health), build-failing.
- Cross-spec dependency on WS5's `tenant_content_overrides` not yet merged. Mitigation: `pack-intake-admin` publish path is dark and its migration row is ordered after WS5's; if WS5 slips, publish stays flagged off and the lane ships intake + linters only.
- Linter false negatives (brand strings in generated copy). Mitigation: case-insensitive scan + immutable-identifier allowlist pinned by test; owner review is the backstop.

## Out of scope
- WS5 persona/greeting/What's New/`tenant_content_overrides` creation (mt-packs / mt-frontend-brand); this spec only publishes INTO that table.
- Per-tenant money, invoicing, Stripe, wallet (M3 / D2/D9).
- Non-engineering owner/ops actions (see Owner decisions): obtaining anchor-person consent, approving Season 0, Exafy legal content sign-off, agreeing revenue share, sending founding invites, the decision to open the tenant.
- Network-scope analytics beyond aggregate member Network activity (mt-network owns scope columns).
- Native app analytics/landing (WS9 / mt-native-health); M2 is web-only.
