# mt-launch — Tenant Launch engineering (WS8): pack intake, content pipeline, tenant-owner analytics, support & landing

<!-- plan:begin -->
## Problem
WS8 engineering (MULTI-TENANT-PLAN.md §6 WS8) is the M2 "a new tenant launches" machinery. Verified today (read-only, 2026-10-15):

1. **Tenant pack intake has no data model.** A tenant's brand/content pack lives only as columns written through `provision_tenant()` and the admin API — `admin-tenants.ts` PACK_FIELDS = `display_name, brand, legal_entity_line, support_email, sender_name, sender_email, default_locale, enabled_locales, timezone, currency, landing, persona_facts` (`services/gateway/src/routes/admin-tenants.ts:383`). There is no record of what intake is still outstanding for a tenant (anchor-person consent, brand kit, Season 0 approval, calendar, seed groups, founding invites, revenue share, health-claims sign-off) — the readiness endpoint (`admin-tenants.ts:536`) only checks the provisioned columns.
2. **No AI-assisted content pipeline.** Nothing generates per-tenant content from Maxina templates, lints it (health claims, leftover `Maxina`/`Mariia`, undated time-bound claims), tracks review/sign-off, or publishes to overrides. The publish target `tenant_content_overrides(tenant_id, locale, key, value)` is WS5's and **does not exist yet** (`supabase/migrations/**` = 0). Health-claim discipline exists only as free-text prompt rules (`community-autopilot/drafts.ts:94`, `anthropic-vision-client.ts:68`), never a linter.
3. **Analytics is member/admin-facing, not tenant-owner-facing, and has no health lineage guard.** `product_analytics_events` (`20260612140000_BOOTSTRAP_product_analytics_events.sql:18`, tenant-scoped, service-role RLS) + daily rollups back `GET /api/v1/admin/tenants/:tenantId/analytics` (`routes/tenant-admin/product-analytics.ts`, `requireTenantAdmin`). There is no tenant-OWNER funnel (signups, activation, journey, events, retention) and **no lint stopping an owner surface reading a health table** (D18). The guard pattern exists for commerce/matching (`test/vtid-05025-commerce-health-boundary.test.ts`, `test/vtid-05156-people-match-health-boundary.test.ts` scan source for a `HEALTH_TABLES` regex) but no analytics equivalent.
4. **Support routing is not per-tenant.** Feedback tickets are created and specialist-detected in the ticket data-plane `routes/feedback-intake.ts` (`handoff-detect`/`start`/`complete`, `KIND_BY_AGENT` Devon/Sage/Atlas/Mira `feedback-intake.ts:32-37`; the voice persona-switch tool `orb/live/tools/live-tool-catalog.ts` is a separate ORB-live concern, NOT the ticket router — corrected per R1-F2); the tenant-scoped admin read exists (`routes/feedback-admin.ts:231` `GET /tenants/:tenantId/tickets`) but there is no per-tenant answerer / SLA / support contact resolution.
5. **Landing SEO/OG is single-tenant in shape, and referral attribution is NOT tenant-scoped (corrected per R1-F1/R1-F5).** `admin-signups.ts:205` dispatches `user.signup.{completed,referral,shared_link}` against the hardcoded `process.env.DEFAULT_TENANT_ID`, so every new-tenant signup/referral is mis-attributed to the default (Maxina) tenant; the invite `/claim` path (`community-invites.ts:54-82`) resolves attribution by code+user with no tenant (line 79 is only an OASIS event payload, not attribution logic). SEO/OG metadata is also Maxina-shaped (OG assets via `tenants` `og_image`, `admin-tenants.ts:471`). There is no per-tenant landing SEO/OG surface, and multi-tenant referral attribution is a real gap this spec must own, not declare done.

## Fix (per lane)
- **`pack-intake-db` (DB, repo vitana-platform).** New `tenant_pack_intake(tenant_id FK tenants, item_key, status, evidence jsonb, decided_by, decided_at, updated_at)` keyed `(tenant_id, item_key)`; `item_key` enumerates the WS8 checklist (anchor-person-consent, brand_kit, copy, persona_facts, brand_kb_docs, season0_approval, events_calendar_90d, seed_groups, host_moderator_support_sla, founding_invites_30, revenue_share, locales, health_claims_signoff). `status IN ('not_started','in_progress','blocked','approved')`. New `tenant_content_pipeline(tenant_id, locale, key, source_template, candidate_value, lint_report jsonb, review_state, reviewed_by, signed_off_by, published_at)`, `review_state IN ('generated','linted','in_review','signed_off','published','rejected')`. Service-role-only RLS (like `product_analytics_events`). Expand-only, no backfill. Read-only `get_tenant_launch_readiness(p_tenant_id)` returns intake completeness for the owner-analytics + readiness surfaces. It is `SECURITY INVOKER` (not DEFINER: the only caller is the gateway service role, which already reads both service-role-only tables, so no privilege elevation is needed), `STABLE`, with `SET search_path = public, pg_catalog` pinned in the definition (repo precedent `20251228000000_vtid_01050_dev_bootstrap_context.sql:23`), owned by the migration role, `REVOKE EXECUTE … FROM PUBLIC, anon, authenticated` and `GRANT EXECUTE … TO service_role`.
- **`pack-intake-admin` (gateway code, repo vitana-platform).** `POST/GET/PATCH /api/v1/admin/tenants/:tenantId/pack-intake` (exafy_admin + tenant-admin per item sensitivity) over `tenant_pack_intake`; the AI-assisted content pipeline: `generateCandidate` (from Maxina templates), three **linters** run server-side as pure functions — `healthClaimLinter`, `leftoverBrandLinter` (flags `Maxina`/`Mariia` case-insensitive outside allowlisted immutable identifiers), `undatedClaimLinter` (flags time-bound claims with no date) — writing `lint_report`; review/sign-off state machine (`generated→linted→in_review→signed_off→published`, `→rejected`); **publish writes to `tenant_content_overrides`** (WS5's table; see Depends on) only from `signed_off`, then i18n seed. **Dependency guard independent of the flag (R1-F3):** the publish repository call maps a missing-relation error (Postgres `42P01`, PostgREST `PGRST205` "Could not find the table") to a typed `DEPENDENCY_NOT_READY` result — the handler answers 409 `{ ok:false, error:"DEPENDENCY_NOT_READY", dependency:"tenant_content_overrides" }`, the row stays `signed_off` (no state change, no partial write), and an OASIS `tenant.content.publish_blocked` event is emitted; no uncaught 500 even if `mt.launch_pipeline` is switched on before WS5 ships. Jest pins both codes. This lane also **creates the per-tenant dark-flag resolver** `services/gateway/src/services/tenant-launch/tenant-feature-flag.ts` — `isTenantFeatureLive(tenantId, key)` reads `tenant_settings.feature_flags.<key>` strictly `=== true`, default OFF, error ⇒ off, cached, modelled on `data-export-consent.ts:79-108` + `data-export-consent-repository.ts:25`. This is NOT `isFeatureLive` (`feature-flags.ts:81`), which is single-arg over a GLOBAL env flag and has no `tenantId`. The pipeline is gated by `isTenantFeatureLive(tenantId, 'mt.launch_pipeline')`; health-claim + leftover-brand linters block publish on any finding, `undatedClaimLinter` warns.

## Tests

- Source-scan guard test (D18): `test/mt-launch-owner-analytics-health-boundary.test.ts`. **Explicit read allowlist (R1-F2):** the owner-analytics modules may name only `product_analytics_events` (`20260612140000…sql:18`), `product_analytics_daily_rollups` (`20260612140100…sql:8`), `tenant_pack_intake`, `tenant_content_pipeline`, `tenants`, and the RPC `get_tenant_launch_readiness`. The test extracts every `.from('…')` / `.rpc('…')` identifier from the scanned files and fails on any name not in that list (fail-closed: an unknown table fails even if it is not a health table), PLUS the inline `HEALTH_TABLES` deny regex below as a second, explicit check. Adding a table to the allowlist is a reviewed one-line edit of the test. **To not block on the unshipped mt-identity (R1-F3), this test defines its own inline `HEALTH_TABLES` regex now, exactly like the existing `vtid-05025-commerce-health-boundary.test.ts:7` pattern** (no import from `isHealthTable()`, which does not exist in the gateway yet). The owner-analytics modules match no `HEALTH_TABLES` regex and import no health repository; a self-test asserts the regex catches a planted read; unknown-provenance tables are not on the read allowlist (fail-closed). When mt-identity ships `isHealthTable()` (O1), this inline list is replaced by importing that canonical predicate — tracked as a follow-up on mt-identity, not a compile-time blocker here.
- pgTAP: `tenant_pack_intake`/`tenant_content_pipeline` reject a client (non-service-role) read; `get_tenant_launch_readiness` is read-only, `SECURITY INVOKER`, has `search_path` pinned (`pg_proc.proconfig`), and `anon`/`authenticated` lack EXECUTE.
- Golden (rule from §6 WS0): the Maxina golden suite is unchanged by this spec (no persona/greeting/push/What's New change here); `npm run test:support` (rule 42c) stays green because support routing adds per-tenant resolution without changing the pipeline contract — any contract change adds a scenario in the same PR.

## Risks
- Publishing generated content to `tenant_content_overrides` could surface un-reviewed strings. Mitigation: publish only from `signed_off`; health-claim and leftover-brand linters hard-block; dark flag; exafy_admin sign-off required.
- D18 leak: an owner-analytics query joining a health table. Mitigation: fail-closed source-scan allowlist (unknown table = health), build-failing.
- Cross-spec dependency on WS5's `tenant_content_overrides` not yet merged. Mitigation: `pack-intake-admin` publish path is dark and its migration row is ordered after WS5's; if WS5 slips, publish stays flagged off and the lane ships intake + linters only.
- Linter false negatives (brand strings in generated copy). Mitigation: case-insensitive scan + immutable-identifier allowlist pinned by test; owner review is the backstop.
- Signup attribution currently hardcodes `DEFAULT_TENANT_ID` (`admin-signups.ts:205`), so founding invites for a second tenant mis-credit Maxina. Mitigation: fixed by mt-jobs VTID-05267 (flag-gated, new user's primary tenant); this spec adds the tenant to the `/claim` invite event (`community-invites.ts:72-80`) behind `mt.launch_support`, proven by a non-default-tenant Jest test; flag off ⇒ unchanged.
- Publishing before WS5's table exists. Mitigation: `DEPENDENCY_NOT_READY` 409 guard on `42P01`/`PGRST205`, independent of the flag.

## Out of scope
- WS5 persona/greeting/What's New/`tenant_content_overrides` creation (mt-packs / mt-frontend-brand); this spec only publishes INTO that table.
- Per-tenant money, invoicing, Stripe, wallet (M3 / D2/D9).
- Non-engineering owner/ops actions (see Owner decisions): obtaining anchor-person consent, approving Season 0, Exafy legal content sign-off, agreeing revenue share, sending founding invites, the decision to open the tenant.
- Network-scope analytics beyond aggregate member Network activity (mt-network owns scope columns).
- Native app analytics/landing (WS9 / mt-native-health); M2 is web-only.
