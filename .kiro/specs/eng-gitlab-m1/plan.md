## 1. Goal
Owner, 2026-11-03: *"we want to have selfhosted GitLab CI in place to speed up our system development and autonomous
self healing and self improvement system."* Milestone 1 is done when:
- GitLab runs at `https://gitlab.vitanaland.com` in a new AWS account `vitana-engineering` (plan `engineering-platform`,
  decision D3), behind an HTTPS load balancer.
- `vitana-platform` and `vitana-v1` are mirrored into GitLab every 5 minutes. GitHub stays the source of truth.
- Every mirrored branch runs the same checks GitHub runs today for these repos (unit tests, typecheck, lint, build) on
  our own runner.
- GitLab backs up nightly to S3, and one restore into a scratch instance succeeds.

Not in milestone 1: agents pushing to GitLab, merge trains, GitLab as source of truth, deploy jobs, autoscaling runners,
self-healing. Self-healing starts after this: failed pipelines become events the system can act on.

## 2. Deliberate deviations from `docs/ENGINEERING-PLATFORM-PLAN.md`, for speed
- GitLab's built-in PostgreSQL and Redis on the GitLab machine, not RDS and ElastiCache (decision D4). Moving to RDS is a
  later task.
- One persistent runner machine (Docker executor, concurrency 4), not the autoscaling fleet (plan §2.2). Autoscaling is
  milestone 2.
- Mirror, not move (decision D1 stage 1 applies after this milestone).
- GitLab Free. No Premium feature is needed in milestone 1 (decision D2 comes before the vitana-v1 cutover).
- Recovery point 24 hours (nightly backup). Recovery time: a rebuild from Terraform plus a restore, hours not minutes.

## 3. Interfaces (fixed here)
- AWS account `vitana-engineering` (created by the owner in AWS Organizations; the management account is
  `472838866351`). Region `eu-central-1`.
- Network: VPC `10.20.0.0/16`, two availability zones. Public subnets hold the load balancer only. Private subnets hold
  the GitLab machine and the runner. One NAT gateway. Nothing in the VPC peers with the production VPC `10.0.0.0/16`.
- Terraform state: S3 bucket `vitana-engineering-tfstate` (versioned, SSE-KMS, public access blocked), locking with
  `use_lockfile = true`.
- GitLab machine: Ubuntu 24.04 LTS (AMI from the public SSM parameter), `m6i.xlarge`, 200 GB encrypted gp3, no public IP,
  IMDSv2 required, administration through SSM Session Manager only. GitLab Omnibus, pinned to one version chosen at lane
  build time from GitLab's release list, `external_url 'https://gitlab.vitanaland.com'`, `nginx['listen_https'] = false`
  (TLS ends at the load balancer).
- Runner machine: Ubuntu 24.04 LTS, `m6i.xlarge`, 100 GB encrypted gp3, Docker, GitLab Runner package, no public IP, no
  inbound rule, IMDSv2 required. Its instance role has no AWS permission.
- Load balancer: HTTPS 443 with an ACM certificate for `gitlab.vitanaland.com`, forwarding to GitLab on port 80.
  Certificate validation and the DNS record live in Cloudflare (the zone of `vitanaland.com`); Terraform outputs both
  records and the owner adds them.
- Security groups: load balancer accepts 443 from the internet. GitLab accepts 80 from the load balancer only. Runner
  accepts nothing inbound.
- Backups: S3 bucket `vitana-engineering-gitlab-backups` (SSE-KMS, versioned, lifecycle deletes after 30 days). A nightly
  `gitlab-backup create` uploads through the GitLab machine's instance role, whose only permission is writing that
  bucket.
- Secrets in AWS Secrets Manager: `vitana/engineering/gitlab/root-password` (generated by Terraform) and
  `vitana/engineering/gitlab/runner-token` (written by the runner bootstrap). No secret in Git or in Terraform state
  values that are not encrypted.
- Mirror: a GitLab project `vitana/ci-mirror` with a scheduled pipeline every 5 minutes. It fetches all branches of the
  two GitHub repositories with a read-only fine-grained token (GitLab CI/CD variable, masked, protected) and pushes them
  to the GitLab projects with a project access token (write_repository).
- Pipelines: `.gitlab-ci.yml` in each repository, using tag `vitana-eng`, no AWS and no deploy job. Commands are copied
  from the repository's own scripts (`services/gateway/package.json` and `package.json` in vitana-v1) and from the Node
  version in `CICDL-GATEWAY-CI.yml`.

## 4. Lanes
Lane `gitlab-infra` (vitana-platform, executor kiro, seat exafy): Terraform in `infra/gitlab-engineering/`, bootstrap
templates for GitLab and the runner, a runbook for the owner, and the structural test. It implements §3 for the account,
network, load balancer, machines, backups and secrets.

Lane `gitlab-ci` (vitana-platform and vitana-v1, executor kiro, seat exafy for platform and exafyltd for v1): the
`.gitlab-ci.yml` for each repository, the mirror pipeline under `infra/gitlab-engineering/mirror/`, and a test per repo
that checks the jobs use the runner tag, reference no AWS, and run exactly the commands the repository's scripts define.
A lane that spans two repositories opens one PR per repository with the same VTID.

## 5. Tests (each red on base)
- `services/gateway/test/eng-gitlab-m1-infra.test.ts` (reads the Terraform text): the GitLab and runner machines have
  no public IP and require IMDSv2; the state backend uses `use_lockfile`; encryption is on for EBS, S3 and Secrets Manager;
  the GitLab security group accepts only the load balancer; the runner has no inbound rule; no IAM statement uses a
  wildcard action with a wildcard resource outside the documented exceptions.
- `services/gateway/test/eng-gitlab-m1-ci.test.ts` and `src/lib/eng-gitlab-m1-ci.test.ts` (reads `.gitlab-ci.yml`): YAML
  parses; every job has `tags: [vitana-eng]`; no job names an AWS credential; each run line is a script that exists in the
  repository's `package.json` or `scripts/`.
- Real checks run by the owner or the lane: `terraform fmt -check` and `terraform validate` output in the lane evidence,
  then `gitlab-runner verify` and the first green pipeline on each project.

## 6. Rollout (owner steps are marked ▶)
1. ▶ Create the AWS account `vitana-engineering` in AWS Organizations and send its 12-digit ID.
2. Lane PRs merge under the owner-named rule (the same way as the first five PRs).
3. ▶ Run `terraform init` and `terraform apply` as the runbook says (about 15 minutes).
4. ▶ Add the two Cloudflare records Terraform prints (certificate validation and `gitlab` pointing at the load balancer).
5. ▶ Log in as root with the password from Secrets Manager. Create the project access token for the mirror. Add the
   read-only GitHub token as a masked, protected CI/CD variable.
6. The runner registers itself with the token from Secrets Manager. `gitlab-runner verify` must pass.
7. The mirror creates the two projects. The first pipelines on `main` must be green: that completes milestone 1.
8. ▶ Restore test: create a scratch instance from the latest backup and compare project counts and one commit hash.

## 7. Cost
Two `m6i.xlarge` machines running all the time, one NAT gateway, one load balancer, 300 GB of encrypted EBS, and S3 for
backups. The lane writes the exact monthly estimate from the AWS price list into its evidence. It is expected to be a few
hundred US dollars per month.

## 8. Risks
- One GitLab machine is a single point of failure. CI stops if it stops. Accepted for milestone 1; high availability is a
  later milestone.
- Untrusted code does not run on the runner in milestone 1 (only our own mirrored branches), and the runner has no AWS
  permission. Both must stay true before agents are allowed to push to GitLab.
- The GitHub token used by the mirror is read-only and limited to these two repositories.
- A GitLab major upgrade needs its own plan. Milestone 1 stays on the pinned version.

## 9. Staging verification and acceptance
Not verified on staging: no product code path changes. Acceptance for milestone 1: GitLab over HTTPS (A01); Terraform
provisioned (A02); encrypted storage and nightly backup (A03); restore succeeds (A04); runner operational (A05); pipelines
green on the mirrored repositories.

## 10. Unchanged
GitHub Actions and every deploy workflow; production; the gateway; production DNS; the production frontend change
(`eng-platform-p02`, paused).
