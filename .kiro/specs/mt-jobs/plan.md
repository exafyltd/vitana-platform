# mt-jobs (WS6): scheduled jobs and automation events loop over active tenants
<!-- plan:begin -->
## Problem
WS6 of the multi-tenant program (`docs/MULTI-TENANT-PLAN.md` §6). The scheduled jobs and
automation-event dispatchers resolve a single tenant from `DEFAULT_TENANT_ID` (= Maxina) and the
EventBridge schedules that drive them send one hardcoded tenant in the body. Verified 2026-10-17 against tip `d4bc696`:
1. **Autopilot heartbeat loop** runs one tenant only: `index.ts:1844` `const heartbeatTenantId = process.env.DEFAULT_TENANT_ID`, `runHeartbeatCycle(heartbeatTenantId)` at `:1853` inside the `setInterval` at `:1848` (registered once at startup). A second tenant's heartbeat automations never fire.
2. **Scheduled-notification routes** take the tenant from the request body or `DEFAULT_TENANT_ID`: `scheduled-notifications.ts:104` `function getTenantId(req)` returns `req.body?.tenant_id || process.env.DEFAULT_TENANT_ID || null`. Every route under it is single-tenant: `/night-push` (route `:1525`, `getTenantId(req)` `:1526`), plus `getTenantId(req)` call sites at `:478,572,750,789,907,1016,1043,1070,1121,1173,1209`. Per-user timezone resolution already exists (`getUserTimezone(supa, user_id, tenantId)` `:1567`, and `:1147`), so only the tenant fan-out is single-tenant, not the per-user clock.
3. **Community scan** (CA-5): `autopilot-recommendations.ts:2281` `router.post('/community-scan', …)` → `runCommunityScan(sb, …)` imported at `:2292`, called at `:2294` (`scan-runner.ts:255` `export async function runCommunityScan(`) processes members whose local hour is 07/17, driven by an hourly EventBridge tick; it has no tenant parameter and reads members platform-wide — but every other member-fan-out around it is tenant-scoped by `DEFAULT_TENANT_ID`.
4. **Morning brief** (`services/gateway/src/services/guide/morning-brief-scheduler.ts:130-131`, note the `guide/` subpath) already fetches each user's `tenant_id` via `fetchUsersForMorningBrief` (`morning-brief-scheduler-repository.ts:38-42`) and passes it through per user (`:140`, `:152`) — re-verified at tip `d4bc696`; the scheduler layer is already tenant-correct, so it stays out of scope. The `/morning-briefing` *route* (`scheduled-notifications.ts:478`) still goes through `getTenantId` and is therefore covered by lane 2.
5. **Memory embedding backfill loop** reads its tenant list from the env var `MEMORY_EMBEDDING_BACKFILL_TENANT_IDS` (`memory-embedding-backfill-loop.ts:38-43`; empty → `{ enabled: false }` at `:43`), not the DB — a new tenant is silently excluded until an operator edits the env.
6. **Automation events** dispatched from member routes. Six sites pin `process.env.DEFAULT_TENANT_ID` directly as the actor tenant: `community.ts:274,382,482`, `match-feedback.ts:280`, `matchmaking.ts:576`, `admin-signups.ts:205` — a member of a second tenant dispatches events tagged as Maxina. The seventh, `groups-events-tools.ts:357-360`, is a different shape: `id.tenant_id || process.env.DEFAULT_TENANT_ID` already tries the session-resolved tenant first and only falls back to Maxina when it is absent, so its common path is already correct and only the fallback is wrong (lane 3 annotates it separately).
7. **EventBridge scripts** pin one tenant by three different mechanisms (re-verified at tip `d4bc696`), none of them a schedule "target input": (a) `setup-eventbridge-whats-new.sh` and `setup-eventbridge-daily-feature-tip.sh` set `TENANT_ID` as a shell var (`whats-new.sh:42`) and bake it into the Lambda's `--environment Variables` (`:204`, `:218`) and the inline handler body `JSON.stringify({ tenant_id: process.env.TENANT_ID })` (`whats-new.sh:158`, `daily-feature-tip.sh:190`); the schedule TARGET JSON (`:270-276`) carries only Arn/RoleArn/RetryPolicy. (b) `setup-eventbridge-cron-migration.sh` bakes `{"tenant_id":"$TENANT_ID"}` into the schedule **Input body** of ~26 jobs (`:156-188`, incl. night-push `:188`, daily-pace `:187`, morning-briefing `:157`, and the memory-embedding-backfill cron `:173`), `TENANT_ID` from `DEFAULT_TENANT_ID` at `:98`. (c) `setup-eventbridge-push-dispatch.sh` pins **no** tenant (nothing to change). So the fix is per-mechanism, not "remove a target input".
Data already present (M0, applied — do NOT re-create): `tenants.is_active` / `is_default` / `is_platform` (`20261014000100`), `tenant_settings.timezone` (`20261014000400`). The active-tenant list and per-tenant timezone are therefore a read, not a migration.
## Fix
Dark by default behind `MT_RESOLUTION_V2` (env master) and `tenant_settings.feature_flags.mt.jobs_tenant_loop`; off ⇒ byte-for-byte today's single-tenant behaviour (reads `DEFAULT_TENANT_ID`). Four code lanes + one governance lane:
1. **`jobs-env-prepare` (executor claude, governance):** stop each script pinning one tenant, per the mechanism Problem 7 identifies. For `whats-new.sh` + `daily-feature-tip.sh`: drop `TENANT_ID` from the Lambda `--environment Variables` block and change the inline handler body from `JSON.stringify({ tenant_id: process.env.TENANT_ID })` to `JSON.stringify({})`, then re-run the scripts so both Lambda config and code are replaced. For `cron-migration.sh`: drop `"tenant_id":"$TENANT_ID"` from each of the ~26 Input bodies so each job fires with a tenant-less body. `push-dispatch.sh` is untouched (pins no tenant). The gateway's own `DEFAULT_TENANT_ID` + `getTenantId(req)` remains the flag-OFF fallback, so no gateway code changes in this lane; `jobs-tenant-loop.ts` (lane 2) does the fan-out when the flag is on. EventBridge infra is Claude-owned → executor claude; Claude/owner re-runs the scripts against AWS (a Kiro lane makes no mutating AWS call). No code reads change until lane 2 ships.
2. **`jobs-tenant-loop` (DB-free code, seat jtadic):** add `services/gateway/src/services/mt-flags.ts` (`isJobsTenantLoopEnabled(env, settings)` reading `MT_RESOLUTION_V2` + `tenant_settings.feature_flags.mt.jobs_tenant_loop`) and `services/gateway/src/services/jobs/job-tenant-loop.ts` — `activeTenantIds(sb)` (`tenants WHERE is_active AND NOT is_platform`), `tenantTimezone(sb, tenantId)` (`tenant_settings.timezone`, fallback `Europe/Berlin`), and `forEachActiveTenant(sb, fn)`. The heartbeat loop (`index.ts:1840-1866`, assignment `:1844`, cycle call `:1853`) and every `scheduled-notifications.ts` `getTenantId`-driven route iterate `activeTenantIds` when the flag is on (one context per tenant), else the single `DEFAULT_TENANT_ID` as today. The `setInterval` is registered once at startup (`index.ts:1848`), so `isJobsTenantLoopEnabled` + `activeTenantIds` are evaluated **inside each tick** (per-tenant `tenant_settings` fetched on that tick), never at init — a mid-flight flag flip takes effect on the next tick with no restart. `mt-flags.ts` + `job-tenant-loop.ts` are the shared gate the brief names — they also gate the mt-launch APIs and the M2 flag flips (stated in 'Depends on').
3. **`jobs-automation-actor-tenant` (DB-free code, seat jtadic):** the six direct-pin sites in Problem 6 resolve the actor's real tenant from the verified identity / primary-tenant lookup instead of `DEFAULT_TENANT_ID` when the flag is on; off ⇒ unchanged. The seventh site, `groups-events-tools.ts:357-360` (`id.tenant_id || DEFAULT_TENANT_ID`), gets the same `resolveActorTenant` treatment but is annotated separately — its `id.tenant_id`-present path is already correct and must stay un-regressed (asserted by a dedicated test). Shares `job-tenant-loop.ts`'s `resolveActorTenant` resolver so the fallback is `resolvePrimaryTenant`, never Maxina.
4. **`jobs-community-scan-tenant` (DB-free code, seat jtadic):** `runCommunityScan` (`scan-runner.ts:255`) and the `/community-scan` route (`autopilot-recommendations.ts:2281`) gain an optional `tenantId`; when the flag is on the hourly tick loops active tenants (scan each tenant's members with that tenant's timezone), else platform-wide as today. The route currently emits one `community_autopilot.scan.completed` OASIS event per call (`autopilot-recommendations.ts:2299-2309`); under the loop it emits **one aggregated** event after the full loop, with each tenant's `ScanRunSummary` collected into the payload — not N events per tick (decision recorded in lane 4). The memory-embedding-backfill loop's tenant source changes from the env var (`memory-embedding-backfill-loop.ts:38-43`) to `activeTenantIds(sb)` when the flag is on (env var stays the override for off/pinned), closing Problem 5.
## Migrations
None. The active-tenant list (`tenants.is_active`/`is_platform`) and per-tenant timezone (`tenant_settings.timezone`) already exist and are applied (M0: `20261014000100`, `20261014000400`). mt-jobs reads them. Spec version range `20261101100000`–`20261101105959` is reserved for mt-jobs in case a later premise re-verification needs one; no row is added to MIGRATION-QUEUE now.
## Tests
- Vitest: `mt-flags.ts` (off when `MT_RESOLUTION_V2` unset; off when the per-tenant flag absent; on when both). `job-tenant-loop.ts` (`activeTenantIds` excludes `is_platform` and inactive; `tenantTimezone` fallback; `forEachActiveTenant` builds one context per tenant). Each converted route/loop: flag off ⇒ exactly one `DEFAULT_TENANT_ID` pass (regression pin); flag on with two active tenants ⇒ two passes, each with its own tenant + timezone.
- Vitest: the seven automation-event sites emit the actor's real tenant (flag on) and `DEFAULT_TENANT_ID` (flag off); `tenant_id` never Maxina for a non-Maxina actor. Dedicated case for `groups-events-tools.ts:357-360`: an `id.tenant_id`-present dispatch keeps using that tenant on both flag states (no regression of the already-correct path).
- Heartbeat flag is evaluated per tick: a Vitest flips `jobs_tenant_loop` off between two ticks and asserts the tenant loop stops on the next tick with no restart (pins R1-F5).
- Community scan: `runCommunityScan` honours `tenantId`; two-tenant loop processes each tenant's members only, and the route emits exactly **one** aggregated `community_autopilot.scan.completed` OASIS event per tick (not one per tenant). Memory-backfill tenant source = DB when on, env when off.
- Keep green (rule 42e): `npm run test:operator` (heartbeat/automation-executor path). `job-tenant-loop` has no live calls.

## Rollout
Dark by default (`MT_RESOLUTION_V2` + `tenant_settings.feature_flags.mt.jobs_tenant_loop`). Merge → staging deploy → STAGING-VERIFY → Gate 2 → PUBLISH, flag OFF. The flag flip to loop all active tenants is an M2 step owned by the mt-launch sequence, after a second real tenant exists (owner-approved). No DB apply (no migration). The EventBridge-script change (lane 1) is applied by Claude/owner against the AWS estate, not by Kiro — a Kiro lane never makes a mutating AWS call.
## Risks
- Flag-on fan-out multiplies per-tenant work on hot tables (`user_notifications`, `chat_messages`); the loop builds one context per tenant and reuses the existing per-user batching — no new per-row cost. Mitigation: Vitest asserts one query per tenant, not per user, for the tenant list.
- A second active tenant with a bad `tenant_settings.timezone` must not break the loop: `tenantTimezone` falls back to `Europe/Berlin` and the per-user `getUserTimezone` still applies. Pinned by test.
- `DEFAULT_TENANT_ID` still read on the flag-off path: removing it is deferred to the M2 flip, not this spec, so a half-rolled-out fleet never loses the single-tenant path.
## Out of scope
- Removing `DEFAULT_TENANT_ID` from the codebase entirely (M2 cleanup after the flag is permanently on).
- The resolution chain / access-token hook / `TenantContext` (mt-identity WS1) — mt-jobs consumes `resolvePrimaryTenant` and the active-tenant read, it does not build them.
- Community-table RLS / scope (mt-community-isolation, mt-network).
- Tenant-owner analytics and the launch content pipeline (mt-launch WS8).

- Done M0: `tenants.is_active/is_default/is_platform` (VTID-05149), `tenant_settings.timezone` (VTID-05150). Read-only.
- **Downstream:** the shared `mt-flags.ts` and `job-tenant-loop.ts` added here gate the **mt-launch APIs** and the **M2 flag flips** — mt-launch depends on this spec's lane 2.
