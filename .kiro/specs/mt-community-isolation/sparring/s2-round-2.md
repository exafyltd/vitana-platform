## Findings

### R2-F1 [major]

The `connect-people` automation handlers (AP-0101/0102/0103) read the `daily_matches` table without any tenant predicate, and the plan's single `connect-people → (M)` mapping does not cover them. `daily_matches` is classified in the plan as a tenant-scoped *content* table (class (i), gets a `tenant_id` column), NOT a per-user table, so the (M) member-id mechanism (`.in('user_id', memberIds)`) is the wrong scope for it. `fetchTopMatch` (:86-94) selects `matched_user_id` by the viewer's `user_id` with no tenant filter, and `fetchReciprocalAcceptedMatch` (:100-107) selects by `matched_user_id`/`user_id` with no tenant filter — after `community-matches-v1` writes a `tenant_id` on insert, a `matched_user_id` from another tenant would still be returned and its name surfaced to a real member via the daily-match/nudge/introduction notifications. The `daily_matches` reads also include `countTodaysUnviewedMatches` (:77-84) and `fetchMatchById` (:96-98), all tenant-less.

Suggestion: Enumerate the `daily_matches` readers in the `connect-people` automation as column-scope (C) reads (`.eq('tenant_id', tenantId)`), not (M), since `daily_matches` is a tenant-scoped content table that gets a `tenant_id` column. Add `fetchTopMatch`, `countTodaysUnviewedMatches`, `fetchMatchById`, and `fetchReciprocalAcceptedMatch` to the explicit per-reader list in the `community-scope-gateway` lane, and add a Vitest case asserting the daily-match deliver/nudge/introduction notification paths only surface same-tenant `matched_user_id`s.

### R2-F2 [minor]

The plan states each social-memory reader "gains a tenantId parameter (breaking signature change)" and the (M) mechanism intersects by-id hydration with `memberIds`, but `fetchPeople` (the hydration function that would receive the memberIds intersection) is a shared chokepoint called internally from many other functions — `fetchFollowEdges` (:151), `fetchMatches` (:231), `fetchRecentMessageContacts` (:287), `fetchUnreadMessageSummary` (:354), `resolvePersonByName`→`fetchPersonById` (:679-681), and `fetchPersonById` (:680) — as well as from `discovery-tools.ts` (:195) and the `persons`/`people` paths. If the memberIds intersection is applied inside `fetchPeople`, every one of these internal callers must thread the tenantId; several of them (the `chat_*`/`fetchRecentMessageContacts`/`fetchUnreadMessageSummary` paths) are explicitly "out of scope / already scoped", yet they call `fetchPeople` and would either need the memberIds set threaded (a behavior change to out-of-scope paths) or would hydrate unscoped. The plan does not specify how the memberIds set propagates through these internal call sites, so an implementer could apply the (M) intersection only at the top-level reader and drop scope at the `fetchPeople` hydration boundary.

Suggestion: Specify explicitly that the memberIds set is threaded into `fetchPeople` (either via a parameter or by intersecting the passed id list before the `.in(...)` call), and enumerate the internal `fetchPeople` call sites (fetchFollowEdges, fetchMatches, fetchRecentMessageContacts, fetchUnreadMessageSummary, fetchPersonById) that must propagate the tenantId/memberIds. For the `chat_*` paths declared out-of-scope, state whether they pass the active tenant's memberIds (redundant-safe since peers are already `.eq('tenant_id')`) or pass an empty/unspecified set, so the behavior is deterministic.
