# VTID-05538 acceptance (eng-gitlab-m2/merge-bot)
Change types: Tooling/docs, Integration.
Outcome: on the self-hosted GitLab (Free tier: no merge trains, no required approvals) a reviewed, green, up-to-date merge request lands by itself, one at a time, as exactly one squash commit with its VTID in the subject; an unreviewed, red, forged or protected-file one does not, and says why once. The module is `scripts/eng/gitlab-land.mjs` (`run`, `merge <project> <iid>`, `status`, `--dry-run`; exports `jobToCheckRun`, `requiredJobsVerdict`, `checksFor`, `decide`, `judgeReviewCommit`, `evaluate`, `tick`, `main`), run by `host/units/vitana-land.timer` every minute.
States: GitLab error half-way (nothing lands), the merge call refused (tried again next tick; the same 60 minutes as a pending pipeline, then the next merge request gets the turn), two ready (oldest first, one per tick), pipeline pending (waits up to 60 minutes), branch behind (updated, not landed in the same tick), branch behind and in conflict with `main` (skipped with one comment, the younger ones go on in the same tick), a force-push after the review (the review no longer counts), a comment already written (not repeated).
Surfaces: merge requests of the projects with `landing: true` in `gitlab-settings.json`; no human screen. Locales and accessibility: n/a.
Contract: plan eng-gitlab-m2 §3.4, including its job-status table. The decisions are the ones of the GitHub pipeline: `land-guard.mjs` (`laneKeyOf`, `localAfter`, `reviewCurrent`, `checksVerdict`, `protectedTouched`, `mergeDecision`) and `queue.mjs` (`commitsInRange`, `PROTECTED_GATE_PATHS`, `GOVERNANCE_PATHS`) are imported and not edited. The GitLab requests it makes are exactly: `GET /projects/:id`, `GET …/merge_requests` (state opened, target main), `GET …/events` (action pushed), `GET …/pipelines` (sha = the head), `GET …/pipelines/:id/jobs`, `GET …/merge_requests/:iid` (re-read after a merge error), `GET`/`POST …/merge_requests/:iid/notes`, and `PUT …/merge_requests/:iid/merge` pinned by `sha`. The test lists them.

AC-4 Waiting and skipping. A pending pipeline waits: no write at all, and the other merge requests of the project are not read or updated. After 60 minutes (from the pipeline's creation) it loses its turn to the next one. A merge request that needs a human (no review, red check, forged accept, protected file, draft, a title that is not `VTID-nnnnn (<slug>/<lane>): …`, a merge of `main` that conflicts) is skipped, not waited for. The same 60 minutes apply to a merge that GitLab keeps refusing (an unresolved thread, a merge setting the bot does not read): the merge request keeps the turn while its pipeline is under 60 minutes old and loses it after that, so the ones behind it are served in the same tick; a dry run makes no merge call, so it never counts as a refusal.

AC-5 A branch behind `main` is brought up to date by merging `origin/main` INTO it (a merge commit, the reviewed head stays an ancestor, never a rebase) as `bot-land`, with the trailer `Collab-Session: bot-land`, pushed without force; it is not landed in the same tick, and the next tick lands it because a clean merge of `main` keeps the review. Decisions taken inside the plan (for Gate 2):
- The review is the newest review of the lane, accept or changes: a `changes` after an accept withdraws it. Plan §3.4 says "the newest `Collab-Verdict: accept` commit"; `queue.mjs` already reads a review window this way (an accept from before a changes round is never reused), so the stricter reading is used.
- A branch behind a `main` that brought in a governance or protected gate file is not updated by the bot. `mergeKeepsReview` ends a review across such a merge, so an update would push a merge commit that makes the next tick refuse the merge request anyway. The bot comments once and the builder merges `main` and asks for a new review. Plan §3.4 says "it merges `origin/main` into the source branch"; for every other behind branch it does.
- A behind branch with a pending pipeline waits (it is not updated early), because `mergeDecision` orders its gates that way and the table test pins identical verdicts. The `merge-queue` lane of plan agentic-delivery changes landing with trains.
- A merge of `main` that conflicts is a skip, not a wait (review of 2026-11-05T14:13Z, blocking). Plan §3.4: "a merge request that needs a human (no review, red check) is skipped, not waited for"; a conflict needs the builder, so the bot comments once per head and the younger merge requests go on in the same tick. Any other failure of the update (a push that fails, for example) still fails the tick and lands nothing.
- A merge that GitLab keeps refusing keeps the turn for the same 60 minutes as a pending pipeline, counted from the pipeline's `created_at`, and then loses it (review, non-blocking; it needs no state between ticks). Plan §3.4 says a refused merge "is retried at the next tick"; it still is, every tick, but it no longer holds the project for ever. Not done: failing closed on a finished pipeline whose own status is not `success` (a failed bridge job): plan §3.4 defines the checks as the jobs of the pipeline, so it is left to lane `merge-queue` of plan agentic-delivery, which edits this file next.
- A reviewer push without `commit_from` proves its tip only (review, non-blocking): the stricter reading, because `commit_count` also counts commits the builder made. The planned flow (the reviewer pushes onto the builder's branch) has a `commit_from` and is unchanged.
- Not changed, with the reason (review, non-blocking): `eventPages` stays 5 (the newest 500 push events; an accept that ages out is refused, never landed; lane `merge-queue`); a landing project with no `required_jobs` is landed on `checksVerdict` alone, as plan §3.4 says, and what the list holds is owned by lane `settings`; the unit runs as root as the plan's unit does (`flock`, `Nice`, `CPUQuota`, `MemoryMax`), a `User=` and sandboxing belong to lane `settings`, which creates the accounts and the token file.
- Only projects whose default branch is `main` are landed: the `land-guard.mjs` functions read `origin/main`. Another default branch is skipped with a log line.
- The bot keeps no state between ticks. The 60 minutes are counted from the pipeline's `created_at` (from the merge request's `updated_at` when there is no pipeline).
- The comment "once per (head, reason)" also applies to `no_review`, as the plan says, so a branch that gets new commits before its review gets one comment per head.
- The configuration is the shape of plan §3.3 (`gitlab-settings.json`: `group`, `projects.<name>.landing`, `required_jobs`), read from the path where lane `settings` puts it. Until that lane is applied there is no such file and the unit does nothing useful; this lane does not install or start anything.

The requirement carried from lane `gitlab-client` is met: `PUT …/merge` is called with `retries: 0` and the merge request is read again after an error.
