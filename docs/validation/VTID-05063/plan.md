## 3. Design

- New file `services/gateway/src/middleware/ledger-read-auth.ts` modelled on `middleware/ledger-write-auth.ts` (VTID-04727). It exports `LedgerReadAuthMode`, `resolveLedgerReadAuthMode(raw = process.env.LEDGER_READ_AUTH_MODE)`, `requireLedgerReadAuth` and `getLedgerReadActor`. It calls the already-exported `evaluateLedgerWriteAuth(req)` (ledger-write-auth.ts:59) so the credential rule cannot drift between reads and writes. The write file is not refactored (scope).
- Env var name: **`LEDGER_READ_AUTH_MODE`**, values `enforce` | `off` | anything else (default) = `log`, exactly like `LEDGER_WRITE_AUTH_MODE` (ledger-write-auth.ts:39-44). Separate from the write variable on purpose: staging writes are already `enforce`; reads have far more callers (the whole Command Hub), so reads need an independent flip and rollback.
- Outcomes in enforce (same as writes): no/empty/non-Bearer header -> **401** `{ok:false,error:"missing bearer token"}`; bad/expired token -> **401** `invalid or expired token`; valid JWT without `exafy_admin` -> **403**; service token or `exafy_admin` JWT -> pass; verifier crash -> **401** (fail closed). An unset or empty `GATEWAY_SERVICE_TOKEN` never authorises (matchesServiceToken, ledger-write-auth.ts:54-57). Verified actor stored on the request for audit (`service:internal` / `admin:<user_id>`).
- Log mode: let the request through and `console.warn` a line tagged `[<VTID>] ledger read would be rejected (mode=log)` with method, route template (`req.baseUrl + req.route.path`, no query string), status, reason, user-agent (first 80 chars, after sanitising) and Origin/Referer host. Origin/Referer is new compared with the write gate and is what identifies unknown browser callers. No tokens, no query values logged. The 403 reason (valid JWT, not `exafy_admin`) is logged distinctly from 401 so the logs also answer "which operators lack `exafy_admin`" (reviewer question 3) without any DB lookup; nobody has checked this yet.
- Log volume and injection control (F7). Every attacker-controlled field (User-Agent, Origin, Referer) is sanitised before it reaches the log: characters outside printable ASCII (0x20-0x7e) and the characters `"` and `\` are replaced by `?`. Lines are deduplicated per key `route + reason + origin host + ua[0:40]` over a 60 s window: the first occurrence logs, later ones increment a counter, and the next line for that key (or a periodic sweep) reports `suppressed=<n>`. Hard caps: at most 200 live keys (oldest evicted) and at most 120 emitted lines per minute per process, after which a single `[ledger-read-auth] log cap reached, dropping` line is emitted per minute. The anonymous-internet case therefore costs bounded memory and bounded log volume, and the Command Hub 5 s/20 s pollers produce one line per minute per route instead of one per poll. Stated in AC-2 and covered by unit tests with fake timers.
- Boot visibility (F5). `ledger-read-auth.ts` also exports `logLedgerReadAuthBoot()`, called once from the `app.listen` callback in `index.ts` (the listen at `index.ts:1649`), logging `[ledger-read-auth] mode=<log|enforce|off> service_token_configured=<true|false>` (presence only, never the value). This makes "enforce is on but no service token is configured on this task definition" visible at boot instead of as a stream of unexplained 401s.
- Read vs write roles: **no difference in Phase 1** (service token or `exafy_admin`). Anything wider (other Command Hub roles, tenant admins) needs a different identity source than `exafy_admin` and is an owner decision (D2, D3). Delegated AI tokens are confined to `/mcp` by `delegatedTokenGuard()` (index.ts:594); not re-verified in depth.
- Placement: per-route middleware argument on each Tier 1 registration, never `router.use` (VTID-04530 lesson). OPTIONS preflights are separate registrations and stay open. HEAD follows GET and is gated.
- Which environment pins what:
  - Code default (no env var): `log` everywhere, including staging and production, after step A.
  - Staging: `LEDGER_READ_AUTH_MODE` is added to the strip list in `.github/workflows/AWS-STAGE-DEPLOY-GATEWAY.yml` in step A so a stray value is removed. Placement (F17): append it AFTER `"SCHEDULED_NOTIFICATIONS_AUTH_MODE",` on the same line (line 1091 reads `..."FEEDBACK_AUTO_DISPATCH_ENABLED","LEDGER_WRITE_AUTH_MODE","SCHEDULED_NOTIFICATIONS_AUTH_MODE",`), giving `..."SCHEDULED_NOTIFICATIONS_AUTH_MODE","LEDGER_READ_AUTH_MODE",`. NOT next to `LEDGER_WRITE_AUTH_MODE`: `test/vtid-04677-scheduled-notifications-auth.test.ts:215` asserts the contiguous string `"LEDGER_WRITE_AUTH_MODE","SCHEDULED_NOTIFICATIONS_AUTH_MODE",` and would fail. It is pinned `enforce` in step B at the pin list (line 1161 holds the `LEDGER_WRITE_AUTH_MODE` pin; add the new pin line after it).
  - Production (F4): **no edit to `AWS-PROD-DEPLOY-GATEWAY.yml` at all.** It runs the code default `log` after step A. Production enforce and production rollback are both `env-only` dispatches of that workflow (section 4), which uses the generic `env_overrides` input (`AWS-PROD-DEPLOY-GATEWAY.yml:240-243`, applied by the generic upsert at lines ~1402-1425, validated as a JSON object, applied last in step 2/2). ## 4. Rollout and rollback

Each step is its own PR through the normal path (PR -> staging -> STAGING-VERIFY -> Gate 2 -> PUBLISH). Never push to production directly. The code of step A reaches production only through the normal PUBLISH path. Production enforce (step D) and production rollback are NOT PRs; they are `env-only` `workflow_dispatch` runs (below). PUBLISH cannot carry `env_overrides` (the workflow comment at `AWS-PROD-DEPLOY-GATEWAY.yml:139-142` says PUBLISH passes only reason/deploy_mode/expected_commit), so these dispatches are a production deploy OUTSIDE the PUBLISH button path. They are therefore one of the autonomy directive's named blockers: the agent does not run them on the strength of `owner-preapproval.md`; it needs the owner's explicit in-session approval for that specific dispatch (CLAUDE.md IF-THEN rule 26 describes this manual-dispatch route and requires scoping it to this change, which `env-only` does by construction because it ships no code).
