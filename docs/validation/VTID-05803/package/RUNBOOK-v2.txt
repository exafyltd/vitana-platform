VTID-05803 execution runbook v2 (no credentials in this file). Replaces RUNBOOK.txt steps 1-5.

Why v2
- schema-restore.sh cannot succeed on the empty staging database. Its eight SQL files are delta scripts for a target
  that a DMS full load already populated. The first file (aurora-cutover-auth-bridge.sql) needs public.app_users,
  and gate 2 requires public to be empty. Reproduced on an empty local Postgres:
    FAIL aurora-cutover-auth-bridge.sql: relation "public.app_users" does not exist
  640 of the 651 public tables the package references are created by none of its files.
- v2 builds the base schema from a schema-only pg_dump of Supabase public, removes the objects that cannot exist on
  Aurora (public->auth FKs, webhook triggers into supabase_functions, views over auth/storage), applies the live API
  grants, then the auth bridge and the outbox. One transaction: an error rolls back everything.
- aurora-cutover-vector-preload.sql is NOT applied: it converts vector columns to text for a DMS load.
  The FK, RLS-parity, grants and views files are superseded by the dump (taken live, not from the 2026-09/10 snapshots).

Most likely cause of the earlier exit code 2 (confirm in CloudWatch; v2 prints STEP markers so one read is enough)
- RUNBOOK v1 step 1 uses bash-only syntax (<<<). Under /bin/sh (dash, busybox) that is a syntax error, exit 2.
- psql also exits 2 when it cannot connect (vitana/aurora/staging/database-url points at vitana-postgres-staging).
- tar exits 2 on "not in gzip format" (Base64 object extracted without decoding).
