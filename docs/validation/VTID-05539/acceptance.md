Decisions taken inside the plan (for Gate 2):
- The topic has its own KMS key, `alias/vitana-engineering-alerts` (plan §3.6 "SNS topic `vitana-eng-alerts` (KMS)"; the brief says to reuse M1's key by reference). CloudWatch can publish to an encrypted topic only when the key policy names `cloudwatch.amazonaws.com`; M1's key has the default policy, which names no AWS service and lives in `main.tf`, which this lane may not edit; the AWS managed key for SNS cannot be edited. Cost 1.00 dollar a month. Everything else of M1 is reused by reference (account id, the GitLab instance, role and load balancer, the backup bucket through the role's existing list permission).
- Recipient (plan §3.6, §9 A6, `tasks.md` States): `alert_email`, which defaults to empty and then falls back to the `admin_email` that `setup.sh` already passes (the owner's address, used for the GitLab root user). The brief gave "empty = a topic without subscription" as an example; that would send nothing to anyone and could not show an unconfirmed subscription, so the default reaches the owner. The plan stops with a message when neither is an address. AWS sends one confirmation mail; alarms reach the owner after the link is clicked.
- The budget mails the owner directly and not through the topic (plan §3.6 names no channel). AWS's own pages disagree on whether Budgets may publish to an encrypted topic, a refusal would fail the whole apply (about 30 minutes), and a direct mail needs no confirmation and no key-policy statement. `monthly_budget_usd` defaults to 1000: milestone 1 costs 452.20 dollars at full size and 284.30 at the start size (`VTID-05544/outputs/cost-estimate.txt`), the fleet manager adds 35.04 (t3.medium at 0.048 an hour), about 12 more secrets 4.80 and this lane 5.66, so the always-on floor is 497.70 (329.80 at the start size); 1000 is twice the floor. The 50 percent mail (500) is therefore a checkpoint that arrives late in most months once jobs run at full size, 80 percent (800) means job machines cost about 300 dollars or more, 100 percent is the stop sign. A healthy month can send that one 50 percent mail; the owner lowers or raises the variable. `outputs/cost-estimate.txt`.
- Evaluation windows (the plan gives thresholds, not windows): the queue alarms need 3 consecutive minutes over the threshold (the oldest pending job) or 30 (the fleet), the host status and load balancer alarms 5 minutes, the disk alarm 3 periods of 5 minutes, the backup alarm 3 periods of 5 minutes, the tick alarms 3 minutes over an age of 900 s. A tick alarm therefore fires 15 to 18 minutes after the last good tick; a single missing minute of the metrics job never raises it.
- Missing data (plan §3.6 names "the heartbeat alarms (host status, backup, tick)" and "the queue alarms"): the disk and load-balancer alarms are `notBreaching`. A quiet disk metric means the agent is not installed yet or has stopped, which the host-status alarm does not cover but a false "disk full" mail would not help; a load balancer with no registered target has nothing unhealthy. A dead host is caught by the host-status alarm (breaching).
- Alarms mail on ALARM only; no `ok_actions` (plan Outcome "a healthy system sends nothing").
- "Fleet at its maximum" (plan §3.6) is read from GitLab, not from the auto scaling group: running or preparing jobs with the tag `vitana-eng` (one job runs on one machine, plan §3.2) against `fleet_alarm_running_jobs` (default 24 = `fleet_max_instances`). Reading the group would need the group's own metrics, which lane `fleet` is not asked to switch on, and a permission on `*` for the host role, which the plan does not name. The cost: the variable must be kept equal to `fleet_max_instances` by hand (its description says so). Jobs of projects the account `bot-metrics` is not a member of are not counted.
- "No completed tick" (not spelled out in the plan): the metrics job reads `systemctl show` of `vitana-land` and `vitana-settings` and keeps the last good completion in `/var/lib/vitana-ci-metrics/ticks.json`, so that no file of lane `merge-bot` or `settings` is edited. The unit names are pinned in the test against `tasks.md` B3 and S4. If a lane renames its unit, the test fails.
- Job ages (plan §3.6 "oldest pending job over 10 min"): see AC-5. The REST Jobs API has no queued-at time; ages of jobs in a running pipeline are a lower bound (a busy fleet that keeps finishing jobs is caught by the fleet alarm, a dead fleet by this one), and at most 25 pipelines are looked up per run.
- The unit runs as root, like `vitana-land`: the token file is written 0600 by the settings sync (plan §3.3) and no Linux user `bot-metrics` is created by any lane; `bot-metrics` is the GitLab account (Reporter). The unit adds sandbox options (`NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=full`, `ProtectHome`). `MemoryMax=512M`, `CPUQuota=50%`: the AWS CLI is the large part.
- The CloudWatch agent package is `latest` from AWS and not pinned; it is installed only after its signature and the AWS key fingerprint verify. The configuration keeps both the series with `fstype` and `path` and the rolled-up `InstanceId` series (two custom metrics). The script exits non-zero when it fails; whether one failing script in `ops.d` stops the others is the decision of `ops-install.sh` (lane `settings`).
- `cloudwatch:PutMetricData` is `Resource: "*"` because the action has no resource-level permission; the `cloudwatch:namespace` condition limits it to `Vitana/Engineering`. The key policy has the usual `kms:*` statement for the account root, without which the key cannot be managed.

The header of `monitoring.tf` says so.
- A project that answers 403 or 404 to the jobs request (CI switched off there) is skipped and logged; every other error fails the whole read. The metrics job reads the projects the account belongs to with `GET /projects?membership=true&archived=false`.
- The backup alarm reads the newest object under `backups/` only; the nightly configuration archive under `config/` is not a backup of the data.
