# 15 — patch 0004: decimal_sum returns numeric on PostgreSQL (+ two HAVING-alias sites)
# Rehearsal 2026-09-14 on the VTID-03840 spike DB (local PG16, port 54329, company f1de441f…),
# worktree /tmp/claude-0/erpclaw-0004 = pin 4d32db6 + patches 0001-0003 committed as base,
# ERPCLAW_HOME pointed at the worktree lib (the module scripts import erpclaw_lib from $ERPCLAW_HOME/lib).

## Why
Every report/GL action that does arithmetic on decimal_sum() failed on Postgres. Root causes (two, not seven):
  (a) the 0002 aggregate's finalfunc returned TEXT, so `COALESCE(decimal_sum(a),'0') - COALESCE(decimal_sum(b),'0')`
      is text - text, and `COALESCE(decimal_sum(x), 0)` is text vs integer. SQLite coerces; Postgres does not.
      51 COALESCE(decimal_sum(…)) call sites (reports 34, gl 9, selling 5, inventory 2, buying 1).
  (b) `si."outstanding_amount" + 0 > 0` (reports check-overdue) — raw text column in arithmetic. Upstream already
      replaced the same idiom elsewhere with CAST(... AS NUMERIC) (party_ledger_residual), so the fix follows precedent.
  (c) surfaced only once (a) was fixed: `HAVING d != 0 OR c != 0` (reports cash-flow) and
      `HAVING total_debit != 0 OR total_credit != 0` (gl _close_pl_accounts) — output-column aliases in HAVING,
      which Postgres disallows. Fixed by repeating the aggregates, again per upstream's own precedent.

## Upgrade semantics
Fast path: `SELECT prorettype = 'numeric'::regtype FROM pg_proc WHERE proname='decimal_sum' AND prokind='a'` → return.
Slow path (advisory lock, as 0002): DROP AGGREGATE only when the existing one is not numeric; DROP FUNCTION IF EXISTS
the old finalfunc; CREATE AGGREGATE without a finalfunc (stype numeric ⇒ result numeric). Idempotent; a second open is a no-op.
Python contract unchanged: psycopg2 returns Decimal; call sites do to_decimal(str(row[...])) and str(Decimal) == the old text.
SQL-level CAST at the 51 call sites was rejected: SQLite NUMERIC affinity loses exactness, and 51 edits vs 1 installer.
