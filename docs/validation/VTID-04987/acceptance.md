# VTID-04987 — CloudWatch alarms in the Overview cockpit + gateway ALB target-health alarm

Plan C. Sparring record: `plan-sparring.md` (3 rounds, CONVERGED, owner-approved 2026-10-08).
Builds on the Overview cockpit (VTID-04876 / 04885 / 04886 / 04887).

What changed:
- `@aws-sdk/client-cloudwatch` is a gateway dependency (same release as `client-cloudwatch-logs`,
  3.1135.0; lockfile regenerated by npm, additive only).
- New `services/gateway/src/services/ops-attention-cloudwatch.ts`: one read-only call,
  `DescribeAlarms(StateValue=ALARM)`, metric + composite alarms, paginated, capped at 100.
- The `cloudwatch_alarms` source is wired into `/api/v1/ops/attention` behind
  `OPS_ATTENTION_CLOUDWATCH_ENABLED` (exact `true`), set on staging only.
- Two operator scripts, dry run by default: the task-role read grant and the
  `vitana-gateway-{prod,staging}-no-healthy-targets` alarm.

No live endpoint or database was called while building this, and every test uses a fake SDK client.
The only AWS calls were the four script dry runs. They are read-only (`sts get-caller-identity`,
`ecs describe-services` / `describe-task-definition`, `iam get-role-policy`,
`elbv2 describe-target-groups`, `sns list-topics`, `cloudwatch describe-alarms`) and their output
is in `outputs/`. Neither script was run with `--apply`.

## The read

AC-1: `describeAlarmsInAlarm()` sends `DescribeAlarms` with `StateValue: 'ALARM'` and
`AlarmTypes: ['MetricAlarm', 'CompositeAlarm']`, and follows `NextToken` to the end. It keeps at
most 100 alarms, and when more remain it returns `truncated: true`. The adapter turns that into a
`partial_error`, so the source reads UNKNOWN but still shows what it found. The region is
`AWS_REGION`, else `eu-central-1`. The whole read is bounded at 5 s across all pages, and the
request is aborted at the deadline.

## The rubric

AC-4: An alarm in ALARM whose name starts with `vitana-gateway-prod-` is P1. Every other alarm in
ALARM is P2, including `vitana-gateway-staging-*` and look-alikes that only contain the prefix.
Every item is in the `platform` domain.
TEST: services/gateway/test/vtid-04987-ops-attention-cloudwatch.test.ts ("P1 = an alarm in ALARM named vitana-gateway-prod-*; every other alarm in ALARM = P2 (staging included)")

AC-5: Items deep-link to the platform tile's existing screen, `overview/system-overview`, which
is checked against `NAVIGATION_CONFIG` in app.js. The evidence holds the alarm name, namespace,
reason and state time. `since` is the alarm's own state time with no second hold, because
CloudWatch already held the condition for its evaluation periods.
TEST: services/gateway/test/vtid-04987-ops-attention-cloudwatch.test.ts ("items deep-link to the platform tile screen and carry name, namespace, reason and state time")

**Naming convention.** Every alarm about the production gateway must be named
`vitana-gateway-prod-…` to page as P1. The constant is `GATEWAY_PROD_ALARM_PREFIX` in
`ops-attention-adapters.ts`, and the convention is written in the alarm script's header.

## Operator scripts

AC-11: `scripts/aws/setup-gateway-cloudwatch-read-grant.sh --env staging|prod` makes changes
only with `--apply`. It refuses any account but 472838866351. It resolves the task role
dynamically: cluster `Vitana-ECS-Cluster`, then service `vitana-gateway-awsdr` (prod) or
`vitana-gateway` (staging), then the live task definition, then `taskRoleArn`. It puts one inline
policy that grants `cloudwatch:DescribeAlarms` on `"*"` and nothing else. It then verifies
read-only with `iam simulate-principal-policy` for the role and one `cloudwatch describe-alarms`.
The dry runs found that staging and prod use the same role, `vitana-ecs-task-role`.
TEST: services/gateway/test/vtid-04987-ops-attention-cloudwatch.test.ts ("the grant resolves the task role from the live task definition and grants cloudwatch:DescribeAlarms only")
UI: outputs/dry-run-grant-staging.txt, outputs/dry-run-grant-prod.txt (read-only dry runs, exit 0)

AC-12: `scripts/aws/setup-gateway-alb-health-alarm.sh --service vitana-gateway-awsdr|vitana-gateway`
makes changes only with `--apply`. It resolves the service, then `loadBalancers[].targetGroupArn`,
then the target group by ARN, then its ALB, all from AWS and never by target-group name. A
comment cites the trap: `vitana-tg-gateway-prod` serves STAGING, and the staging dry run resolved
exactly that group. The alarm is `vitana-gateway-prod-no-healthy-targets` for prod and
`vitana-gateway-staging-no-healthy-targets` for staging: `AWS/ApplicationELB HealthyHostCount`,
Minimum < 1, 2 × 60 s, `TreatMissingData=breaching`, with alarm and OK actions to the existing SNS
topic `vitana-alarms-prod`. The topic is resolved by name, and the script refuses if it is
missing. The header documents the trade-off and the naming convention.
TEST: services/gateway/test/vtid-04987-ops-attention-cloudwatch.test.ts ("the alarm resolves service → target group → ALB from AWS, never by target-group name, and refuses without the SNS topic")
UI: outputs/dry-run-alarm-vitana-gateway-awsdr.txt, outputs/dry-run-alarm-vitana-gateway.txt (read-only dry runs, exit 0)

**`TreatMissingData=breaching`, the trade-off (plan F6).** For a production gateway, "no data"
and "no healthy targets" both mean "page someone". The ALB stops emitting `HealthyHostCount` when
the target group has no registered targets at all, which is the outage this alarm exists for.
The cost is that an intentional drain also pages. That is rare, and the alarm description says to
disable the alarm's actions for a planned drain rather than weaken the alarm.

## Staging limit

The read-only STAGING-VERIFY suite cannot sign in, so it proves only that the gateway is alive
and that `/api/v1/ops/attention` is still mounted and admin-gated (401 JSON). Whether
`cloudwatch_alarms` reads `ok` on staging can only be confirmed signed in, by an exafy_admin on
the staging Command Hub Overview. The Platform & Services tile should show "Sources fresh 2/2"
and no "Not yet monitored" note. An admin-token `GET /api/v1/ops/attention` should have
`sources[]` with `cloudwatch_alarms` → `ok`. Before the grant is applied, that source reads
`unknown` with an AccessDenied error. That is the honest state, never green.

## Rollout order

1. **Grant on staging.** An operator with IAM rights runs
   `scripts/aws/setup-gateway-cloudwatch-read-grant.sh --env staging --apply` before the merge.
   The dry runs show that staging and prod share `vitana-ecs-task-role`, so this one grant also
   covers prod. That is harmless, because prod's flag stays off. The session user is denied IAM
   reads and writes on that role (`outputs/dry-run-grant-*.txt`), so a session cannot apply it.
2. **Merge.** The PR turns the flag on for staging only, and the staging deploy picks it up.
3. **Staging verify.** STAGING-VERIFY runs `staging-tests.json`. A signed-in admin then confirms
   the source reads `ok` (see "Staging limit").
4. **Alarm `--apply`.** Run `scripts/aws/setup-gateway-alb-health-alarm.sh --service vitana-gateway-awsdr --apply`
   and `--service vitana-gateway --apply`, by the owner or by the session after the owner OKs the
   dry run in `outputs/`.
5. **Prod grant.** Run `setup-gateway-cloudwatch-read-grant.sh --env prod --apply`. It re-puts the
   same policy on the same role, so it is idempotent; the verification step confirms it.
6. **Prod flag PR.** A small follow-up PR under the same VTID sets `OPS_ATTENTION_CLOUDWATCH_ENABLED=true`
   in `AWS-PROD-DEPLOY-GATEWAY.yml`. It carries its own `staging-tests.json` that re-runs the
   read-only staging probes, and its body cites the green staging run from step 3. It reaches
   production only through the ready message and PUBLISH.

Rollback at any point: set the flag to `false`, or remove it. The source is then shown as not
monitored, and no code is reverted.
