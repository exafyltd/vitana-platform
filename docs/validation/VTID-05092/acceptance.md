AC-13 **Withdrawal always works (GDPR Art. 7(3)), even before the migration is applied.** When `fn_set_health_consent` is missing, a revoke on the new route (`POST /api/v1/health/consents/revoke`) and on the legacy route (`POST /api/v1/partner-health/consent/revoke`) falls back to the pre-WP1 write: `UPDATE data_sharing_consents SET revoked_at = now()` on the member's own active row(s) for that resource_type/resource_id/scope (pre-migration columns only), then the audit row in `data_sharing_consent_events` with pre-migration columns only. It answers 200 with the normal revoke shape (`text_version`/`shown_locale` null) and emits `health.consent.revoked`. If the audit insert fails, the revoke still answers 200 (the withdrawal takes precedence over the audit row — code comment cites Art. 7(3)), the failure is logged as `AUDIT ROW MISSING` and counted (`getConsentAuditFailureCount()`). Revoking a consent the member does not hold is 200 `changed:false` with no write. A grant stays fail-closed (503 `CONSENT_STORE_PENDING`, nothing written) on both routes. The legacy GET and the ingestion consent check (`checkDataSharingConsent` / `hasHealthConsent`) keep working pre-migration. After the migration every path goes through the function only (no direct table write). Proven with the real service and both real routers over a strict in-memory copy of the pre-migration schema that rejects any new column, table or function exactly as PostgREST does (mutation-checked: adding a new column to the fallback's audit insert, or returning 503 for a revoke, fails the suite).

## Rollout notes (from the plan)
- Staging runs this gateway with the migration **unapplied**: `GET /api/v1/health/consents` → `store_pending:true`, grants (new and legacy) → 503 `CONSENT_STORE_PENDING`, revokes (new and legacy) → 200 through the pre-migration write (AC-13), `checkDataSharingConsent`/`hasHealthConsent` unchanged (pre-migration columns).
- At Gate 2 "yes": apply this migration to production first, **then** dispatch the gateway prod deploy pinned to the verified commit. If someone else's PUBLISH ships this code before the migration (it has happened twice), members can still withdraw every consent (AC-13); only new grants wait for the migration.
- Before Gate 2: the read-only production count from Rollout step 3 (active consents by resource_id, unresolved consent_missing rows, active wearable user_connections).
