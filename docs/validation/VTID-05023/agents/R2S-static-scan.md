## What matters most

- Three return-type changes (c) fail a replay of the migration set in name order. Each `CREATE OR REPLACE` changes a RETURNS TABLE column list while the old function still exists. `pick_specialist_for_text` and `get_autopilot_recommendations` get a DROP FUNCTION only in later files. `get_pending_worker_tasks` has no DROP FUNCTION at all.
- Seven policy re-creates (f) collide with a policy that an earlier file already created under the same name and table, so they error when the set is replayed.
- `wallet_transactions` is written to and read from with columns such as `from_user_id`, `to_user_id`, `from_currency`, `to_currency`, `transaction_type`, and `fees` that no top-level migration adds (d). The table created in `20260318000000` lacks them. The header of `20260704060000` says the live table has them, so they were created outside the migration files.
- Four ON CONFLICT clauses on `relationship_edges` (functions in `20251231000001_vtid_01090`, `_01091` (two), and `_01094`) use target columns (`source_type`, `source_id`, `target_type`, `target_id`, `edge_type`, `source_user_id`, `target_user_id`) that the table does not have. No unique index on those columns exists in the migrations. The statements sit in function bodies, so they fail when the function runs, not when the migration applies.

## Method

- Input: the 733 top-level `.sql` files in `supabase/migrations`, in `LC_ALL=C` name order. `data-fixups/` and other subdirectories were not scanned.
- Tool: a scratch Python scanner outside the repo, at `/projects/sandbox/agents/R2S-scratch/scan.py`. It strips comments, respects quoted strings and `$tag$` bodies, and splits on top-level `;`. It is not a Postgres parser.
- Catalog: it replays every top-level DDL statement in name order (CREATE/ALTER/DROP TABLE, CREATE/DROP INDEX, CREATE/DROP FUNCTION/PROCEDURE, CREATE/DROP POLICY, CREATE TRIGGER). DDL inside DO blocks is also applied, and `IF ... THEN` prefixes are skipped. `CREATE TABLE IF NOT EXISTS` is a no-op when the table already exists, as in Postgres.
- Function and procedure bodies run later, so ON CONFLICT, INSERT, UPDATE and column checks inside them use the end-of-set catalog. Top-level statements and DO blocks use the catalog at their position in name order.
- (a): an ON CONFLICT (cols) target matches a unique index or PK only when the column sets are equal. A partial unique index matches only when the ON CONFLICT clause repeats the same WHERE predicate, compared as normalized text.
- (d): a column is absent when no CREATE TABLE, ADD COLUMN, or RENAME COLUMN in the set creates it. This checks only the migration set.
- (e): NOT NULL without DEFAULT, excluding identity, serial and generated columns. An INSERT with no column list is not checked. A BEFORE or INSTEAD OF INSERT trigger on the table downgrades the hit to POSSIBLE. An AFTER trigger does not, because it runs after the NOT NULL check.
- (f): a hit means no DROP POLICY IF EXISTS for the same policy name and table appears earlier in name order, and the CREATE is not inside a DO block that checks `pg_policies`, catches an exception, or drops the policy.
- (c): Postgres rejects CREATE OR REPLACE when the RETURNS type changes (including RETURNS TABLE columns), when an input parameter is renamed, or when an existing default is removed. A changed input type list creates an overload instead, so it is listed as (c-args).

## Limits and caveats

1. (b) transaction wrapping. The scan sees no explicit BEGIN around the five `CREATE INDEX CONCURRENTLY` statements in `20260205000000_fix_oasis_events_disk_io_indexes.sql` and `20260916150000_vtid_03972_widen_oasis_events_retention.sql`, and none sits in a DO block. Supabase says its migration runner handles transaction atomicity itself, and a CLI issue reports that CONCURRENTLY fails inside a pipelined batch ([Supabase KB](https://supabase.com/kb/troubleshooting/partial-migrations-and-schema-inconsistencies-from-embedded-transactions-13ae82), [supabase/cli#2898](https://github.com/supabase/cli/issues/2898)). Whether the runner wraps each file is not visible in the repo. If it does, these five statements fail. That is a POSSIBLE risk, not a pattern hit, and needs a check with the runner the owner uses.
2. Base-schema tables. Tables not created by any migration (`auth.users`, `profiles`, `storage.buckets`, and the tables in the POSSIBLE list under (a)) cannot be checked. Those hits are POSSIBLE.
3. Dynamic SQL. `EXECUTE format(...)` strings and EXECUTE-built policies or DDL are not analyzed. Two (a) hits in `20261102040100` and `20261102041000` sit inside such strings and stay POSSIBLE.
4. Conditional DDL. ADD COLUMN inside `IF NOT EXISTS` checks in DO blocks is applied as if it runs. A column that is added only on some branches may be missed or over-counted.
5. Triggers. Only top-level CREATE TRIGGER statements are read. A trigger created inside a DO block is not seen.
6. Live database. Nothing was queried. Columns and policies created by hand on the live project are invisible here (see the `wallet_transactions` note above).
