## Changes
**A1 — a live room follows its host (vitana-platform, migration + test).** New trigger on `community_live_streams`:
- AFTER INSERT (pending, future `scheduled_for`, creator not a registered test/service account): one host row, source `live_room`/`live_room`, same shape as the subscriber row plus `metadata.host=true`, `reminder_offsets` default. It is the SAME row (unique on user, source_ref_id, source_ref_type) the subscriber trigger would write: if the row already exists (a host who subscribed first, or the one-time backfill below) the host trigger only merges `host=true` into its metadata and keeps its status/times; if the host later taps Erinnern, the subscriber trigger's `ON CONFLICT` leaves metadata alone, so `host=true` survives.
- The subscriber trigger's DELETE branch (replaced via `CREATE OR REPLACE` in the same migration) leaves a row alone when `metadata->>'host' = 'true'`: the host's relationship to the room is `created_by`, not the subscription, so un-notifying must not remove the host's own entry.
- One-time host backfill in the same migration: hosts of streams with status 'pending' and a future `scheduled_for` (today: the one 30 Oct room) get their row; registered test/service accounts skipped; idempotent.
- AFTER UPDATE OF scheduled_for, duration_minutes, title, description, status, with a trigger-level `WHEN (OLD.x IS DISTINCT FROM NEW.x …)` over exactly those columns (the VTID-04915 pattern): set-based UPDATE of every non-cancelled row for that stream (start, end, title, description). Status handling is a WHITELIST: only `'cancelled'` cancels the rows; every other value (the app knows pending, live, ended, cancelled — no database CHECK on the column was found, so a future value must not surprise us) leaves them untouched — the room has started or finished, the entry is history. `scheduled_for` set to NULL → cancelled. Rows that are cancelled are never revived by an UPDATE (only a new subscribe revives, as today).
- AFTER DELETE: every non-cancelled row cancelled.
- The existing subscribe trigger and backfill are unchanged. Throwaway-Postgres test (like VTID-04915's) + Jest pin test + `DATABASE_SCHEMA.md` row. Applied to the shared database only through RUN-MIGRATION after merge, at Gate 2.
**A2 — one reminder, not two (vitana-v1 + a small production data fix).** Remove the personal 10-minute `createReminder` from the three Erinnern call sites (the calendar entry now carries the reminder, and it follows A1 reschedules, which a fixed-time personal reminder never would). The unsubscribe path then has nothing left behind. One-time data fix, run at Gate 2 with the migration: cancel the pending personal reminders created by Erinnern for a room that now has a `live_room` calendar row for the same member. Matching is by time, not by title text: same `user_id`, `created_via<>'system'`, `calendar_event_id IS NULL`, `status='pending'`, and `next_fire_at` within ±2 minutes of that calendar row's `start_time − 10 minutes`. It runs as a read-only listing first and applies only if the count is exactly the 2 measured today (anything else: stop and report, never widen). Tests: drawer/card tests assert no `createReminder` call; staging spec unchanged.
**A3 — personal reminders show in the calendar (vitana-platform migration + gateway types; vitana-v1 display).**
- Migration: the `valid_source_type` CHECK is dropped and recreated with `reminder` added (the same pattern as the 04331 migration), and the gateway's `CALENDAR_SOURCE_TYPES` list (`services/gateway/src/types/calendar.ts:216-221`) gets `reminder` IN THE SAME PR, so the two never disagree.
- Three triggers on `reminders`, each with a trigger-level WHEN so the function never runs for anything else (in particular never for the reconcile's own system rows): INSERT `WHEN (NEW.created_via IN ('voice','ui') AND NEW.calendar_event_id IS NULL AND NEW.recurrence_rule IS NULL)`; UPDATE with the same predicate on NEW plus `AND (OLD.next_fire_at, OLD.status, OLD.action_text, OLD.recurrence_rule) IS DISTINCT FROM (NEW.next_fire_at, NEW.status, NEW.action_text, NEW.recurrence_rule)`; DELETE `WHEN (OLD.created_via IN ('voice','ui') AND OLD.calendar_event_id IS NULL)`. Reminders are one-shot in practice (nothing in the gateway writes `recurrence_rule`); if a reminder ever gains a rule, the UPDATE branch cancels its mirror row.
- Mapping (one row per reminder, `source_type='reminder'`, `source_ref_type='reminder'`, `source_ref_id`=reminder id, `event_type='personal'`, `role_context='personal'`-equivalent lens as the 04331 data model allows, start = end = `next_fire_at`, `timezone` = `user_tz`, title = `action_text`, **`reminder_offsets='{}'`**): `pending`/`dispatching` → row confirmed at `next_fire_at`, `completed_at` cleared (a snooze — `POST /reminders/:id/snooze` sets `next_fire_at = now+N`, `status='pending'` — moves the row and reopens it); `fired` → row stays where it fired; `completed` → row marked completed; `cancelled`/`failed` or DELETE → row cancelled. Both directions are free of loops: the mirror row has no reminders of its own (`reminderRules()` returns `[]` for `'{}'`, `calendar-reminders.ts:91-93`) and nothing writes `reminders` from it.
- Frontend: the calendar screen maps `reminder` entries to a "Reminder" look (existing entry kinds, label in all 11 locales, German first, du-form), opens the existing entry screen read-only for fields it cannot edit (edit/move/cancel go through the reminders API, not the calendar's); "mark done" completes the reminder through the existing reminders endpoint or is hidden — decided in implementation and listed at Gate 2.
- Tests: SQL behaviour test, Jest pin, vitest for the display, calendar goldens re-recorded only for the new kind; staging spec read-only (the Calendar page still renders; no write).
