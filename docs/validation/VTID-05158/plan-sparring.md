**S1 — wire contract and device pre-aggregation (Health Sync v1).** C owns the only external schema. A publishes no wire schema and no public ingest route. C1 owns `routes/health-ingest.ts`, its mount and path-scoped body parser in `index.ts`, the HTTP rate limiter, `GET /contract` and `GET /status`. C's adapter `processHealthSyncBatch` turns a validated v1 batch into the S3 input; that TypeScript input type is A's internal type, not a second schema. Wire limits are C's (512 KB compressed, 4 MB inflated, ≤ 1,000 records + ≤ 1,000 deletions). Each record's `type` is an S2 key with `kind` `series_sum`, `series_stats` or `record`:
- **Series codes** (`series_sum`, `series_stats`): the app pre-aggregates on the device (HealthKit statistics collection query / Health Connect aggregate by duration) into aligned UTC intervals: 5 minutes when `start` is within the last 30 days, 1 hour when older. There is one item per interval with `record_id = "<type>:<start, ISO-8601 UTC>"`. A `series_sum` item carries `value` (the interval sum). A `series_stats` item carries `stats:{n,sum,min,max}`. When an interval changes, the app re-sends the whole interval (the result is `updated`). An interval whose samples are all gone is sent as a deletion of that `record_id`. No per-sample rows exist anywhere.
- **Record codes** (sleep session with stages, workout, weight, body fat, spot values): one item per OS object, `record_id` = HKObject UUID / Health Connect `metadata.id`.
- **Idempotency:** batch level `(user_id, batch_id)` and record level `(source_id, record_id)`. For series items the record key equals A's bucket key `(source_id, code, bucket_start)`, so the two rules are one rule.

**S3 — `writeHealthSamples`.**
```
writeHealthSamples(sb, {
  identity: { tenant_id, user_id },        // from the JWT or the server-side caller, never from a body
  source_id,                               // health_sources.id (S6)
  batch_id,                                // uuid: the wire batch_id, or a new uuid per server-side call
  via: 'health_sync_native'|'health_sync_aggregator'|'internal'|'reprocess',
  tz?, contract_version?,
  samples:   [{ source_record_id, code, unit, start, end?, tz?, value?, stats?:{n,sum,min,max},
                device?, origin_app_id?, detail? }],
  deletions: [{ source_record_id, code }],
}) → { ok:true, replay:boolean, batch_id,
       results:[{ source_record_id, status, code? }] }
   | { ok:false, code:'STORE_DISABLED'|'STORE_PENDING'|'STORE_UNAVAILABLE'|'SOURCE_NOT_CONNECTED'
                     |'BATCH_ID_REUSED'|'QUOTA_EXCEEDED'|'INVALID_INPUT' }
status ∈ stored | updated | duplicate | deleted | not_found | quarantined | invalid | skipped_no_consent | store_unavailable
```
- **Never throws.** Every failure is a result. A Jest test injects a throwing repository, S3 client and consent read.
- **Order:** store flag (`STORE_DISABLED`, nothing read) → source lookup through S6 (an unknown source or another member's source gives `SOURCE_NOT_CONNECTED`) → batch idempotency → consent per sample (S7) → raw archive of the consented subset → validation and quarantine → store write in chunks of ≤ 2,000 → batch row → change hook if anything was deleted (S8).
- **Consent is inside, per sample category, fail closed.** The consent id is stored on every row and on the batch row. An unconsented sample is `skipped_no_consent` with `code` `CONSENT_REQUIRED`, or `CONSENT_CATEGORY_MISSING` when no D10 key exists. It is never archived, never quarantined, and only counted. Callers may filter first (C does); A still checks.
- **Replace mode is the only mode.** The key is `(source_id, source_record_id)`. Identical content gives `duplicate`; different content replaces the stored row and gives `updated`. There is no `replace` flag. B's replace-semantics writers get this from deterministic keys (`<writer>:<date>:<code>`); event writers use a new uuid per call.
- **Batch replay:** the same `batch_id` with the same normalised-content hash within the 30-day batch retention returns the stored results with `replay:true` and writes nothing. Different content gives `BATCH_ID_REUSED`.
- **Validation codes** (`code` on `quarantined`): `UNKNOWN_CODE`, `CATEGORY_NOT_ALLOWED`, `UNIT_MISMATCH` (unit ≠ catalogue UCUM unit), `IMPLAUSIBLE`, `MISALIGNED_BUCKET`, `TOO_OLD` (`start` older than 400 days or before the earliest partition), `FUTURE` (`end` more than 5 minutes ahead). A quarantine row stores no value. `invalid` (code `INVALID_ITEM`) is a malformed item and is not quarantined.
- **Raw archive** (A's S3 bucket) receives only the consented subset, serialised from this input, never the original request bytes.
- **Limits and quota:** ≤ 5,000 samples + deletions per call. A's per-member DB quota answers `QUOTA_EXCEEDED`.
- **Latency:** p95 ≤ 150 ms for ≤ 10 samples, in process, S3 put included. Jest pins the round trips (one consent read per category present, one S3 put, one RPC per chunk). The 0T load run measures the number, and the result is a condition for activating B2's dual-write.
- `STORE_PENDING` when the store's tables or functions are absent (D10 `isConsentStoreMissing` pattern); nothing is written. `STORE_UNAVAILABLE` covers S3 or database failures.
- **Mapping to Health Sync v1 (C1):** `STORE_DISABLED` → 409 `INGEST_DISABLED` (`reason:'flag_off'`); `STORE_PENDING` → 503 `STORE_PENDING`; `STORE_UNAVAILABLE` and `SOURCE_NOT_CONNECTED` → 503 `STORE_UNAVAILABLE`; `BATCH_ID_REUSED` → 409 `BATCH_ID_REUSED` (not retryable; a new row in C's table); `QUOTA_EXCEEDED` → 429 `RATE_LIMITED`; `INVALID_INPUT` → 400 `INVALID_BATCH`. Per record: `IMPLAUSIBLE` → `IMPLAUSIBLE_VALUE`; `UNIT_MISMATCH` → `UNIT_MISMATCH`; `UNKNOWN_CODE`/`CATEGORY_NOT_ALLOWED` → `UNSUPPORTED_TYPE`; `TOO_OLD`/`FUTURE` → `OUT_OF_WINDOW`; `MISALIGNED_BUCKET`/`INVALID_ITEM` → `INVALID_RECORD`; `skipped_no_consent` → `CATEGORY_NOT_CONSENTED`; `store_unavailable` (a chunk that still failed after one partition-ensure retry; alarm `health.store.partition_missing`) → `STORE_UNAVAILABLE`, retryable; `stored`/`updated`/`duplicate`/`deleted`/`not_found` go into the counts. B2 logs and counts every `ok:false` and non-stored status. These are non-fatal in dual-write mode and fatal only in `derived` mode.
- **Flags:** the ingest route needs C's `HEALTH_SYNC_INGEST_ENABLED` **and** A's `HEALTH_STORE_ENABLED` (+ `HEALTH_RAW_BUCKET`). Both are forced off when `VITANA_ENV=staging`.

**S4 — reads.**
```
readDailyObservations(sb, identity, { codes, from, to, purpose })
  → { ok:true, rows:[{ date, code, value, unit, sample_count, updated_at,
                       sources:[{ source_id, source_kind, value, sample_count }] }] }
  | { ok:false, code:'consent_required'|'PURPOSE_REQUIRED'|'STORE_DISABLED'|'STORE_PENDING'|'STORE_UNAVAILABLE' }
```
- `purpose ∈ 'member_view'|'feature_compute'|'ai_context'` is mandatory and has no default. A missing purpose gives `PURPOSE_REQUIRED`, and the repository is not called.

The consent id is stored on every row and batch. The gate is an interface: the Phase 1 consent package replaces the implementation with per-data-category consent without touching ingest. Suppression primitives (1l) are the storage half of withdrawal: suppressed rows are unusable at once, undo within 7 days, hard-deleted by the purge after 7 days; withdrawal also deletes the member's raw batches of that source (Change 8). **Trade-off (round-1 F4), deliberately conservative:** a raw batch mixes categories, so a "delete history" withdrawal of one category deletes **all** raw batches of that source for the member; stored aggregates and records of the categories that are still consented survive untouched (suppression is per category); the only loss is the ability to reprocess that source's last ≤ 30 days of raw input, which is a convenience, never the system of record. This errs toward erasure (GDPR Art. 7(3)/17). Wiring revoke → suppress is the consent package's.
7. **Ingest pipeline** (`ingest.ts`, `writeHealthSamples`, S3; no HTTP route of its own, `index.ts` only mounts the internal router next to `:1167`): flag (Change 10, `STORE_DISABLED`) → source lookup (S6) → per-member DB quota (≤ 500 batches and ≤ 50,000 items/day, ≤ 250,000 during the 7 days after a source's first batch; `QUOTA_EXCEEDED`) → **idempotency**: same `(user_id, batch_id)` with the same normalised-content hash → stored results with `replay:true`, different hash → `BATCH_ID_REUSED` → consent gate → **write the consented subset to S3** (`raw-batch-store.ts`, key `u/<user_id>/<source_id>/<yyyy>/<mm>/<dd>/<batch_id>.json.gz`, SSE-KMS; failure → `STORE_UNAVAILABLE`, nothing in Postgres) → per-item validation (S3 codes: unit = catalogue unit, plausibility, alignment, `FUTURE` > 5 min, `TOO_OLD` > 400 days or before the earliest partition) → invalid items to quarantine → `health_store_ingest` in ≤ 2,000-item chunks (missing function/table → `STORE_PENDING`, D10's `isConsentStoreMissing` pattern; **partition-routing error** — SQLSTATE `23514` or message `no partition of relation … found for row` — → call `health_store_ensure_partitions(now())` once, retry that chunk once; if it still fails, every sample of that chunk gets per-sample status `store_unavailable` (not stored, not quarantined, retryable by the caller), with a structured log line and alarm code `health.store.partition_missing`; other chunks are unaffected and the call never throws) → batch row → change hook if rows were deleted (S8) → per-sample results. It never throws; errors are codes, never DB messages. The HTTP mapping is C's (S3 table).
   **OASIS** (declared in `types/cicd.ts`): `health.store.source.first_data`, `health.store.batch.quarantined` (counts only), `health.store.quota.exceeded`, `health.store.maintenance.completed|failed`, `health.store.partition_missing` — all added to the `CicdEventType` union (F20), and the `health.store.*` namespace is documented with the tables in the `DATABASE_SCHEMA.md` update (round-1 F6). Payloads carry ids and counts, never values. Per-batch success is telemetry, not an OASIS event: the handler carries an `impact-allow-no-oasis` opt-out with that reason (counts live in `health_ingest_batches` and structured logs).
   **Internal routes** (`routes/health-store-internal.ts` at `/api/v1/health/internal`): `POST /maintenance` (`X-Gateway-Internal`, F16) runs ensure → purge, single invocation; `POST /reprocess {batch_id}` (`requireServiceOrAdmin`) re-reads the S3 batch and runs `writeHealthSamples` again (`via:'reprocess'`) with the **current** consent and catalogue (idempotent by replace); `POST /erase-raw {user_id, source_id?}` (Change 8); `GET /store-status` (`requireAuthWithTenant`) → `{enabled, reason}` (`getHealthStoreStatus()`, also embedded by C's `/api/v1/health/ingest/status`) for staging verification and the go-live check.
8. **Raw-batch erasure.** `erase-raw` deletes every object under `u/<user_id>/` (or `u/<user_id>/<source_id>/` for a withdrawal), then lists again and returns `{deleted, residual}`. The bucket is unversioned, so a delete is final.
9. **Reader and purpose boundary** (`reader.ts`, S4): `readDailyObservations` plus `readSeries5m`, `readHourly`, `readRecords`; every read filters `suppressed_at is null`, takes identity + mandatory `purpose`, enforces `ai_health_analysis` for `ai_context` via `hasHealthConsent` (fail closed → `consent_required`). `tables.ts` exports `HEALTH_STORE_TABLES` (S5). The vtid-05025 boundary test (F18) adds `HEALTH_STORE_TABLES` to `HEALTH_TABLES` and forbids commerce modules from importing `services/health-store/*`. `change-hook.ts` exports `registerHealthStoreChangeHook` and `suppression.ts` the `suppressHealthData`/`unsuppressHealthData` wrappers that fire it (S8/S9).
10. **Dark flag** (`flags.ts`): enabled only when `HEALTH_STORE_ENABLED === 'true'` **and** `VITANA_ENV !== 'staging'` **and** `HEALTH_RAW_BUCKET` is set. Off → `writeHealthSamples` and the readers answer `STORE_DISABLED` without reading anything, and the internal routes answer `404 {error:'HEALTH_STORE_DISABLED'}` without reading the body; `GET /api/v1/health/internal/store-status` says why. Production and staging task defs do not get the flag in this package.
11. **Infra scripts (dry-run default, owner-run `--apply`, F11/F16 patterns).** `setup-health-raw-bucket.sh <env>`: bucket `vitana-health-raw-<env>` in `eu-central-1`, Block Public Access, SSE-KMS with a dedicated CMK `alias/vitana-health-raw-<env>` + bucket key, versioning off, lifecycle expire 30 days + abort multipart 1 day, TLS-only policy, access only for the gateway task role (Put/Get/Delete/List on the bucket, GenerateDataKey/Decrypt on the key). `setup-eventbridge-cron-migration.sh`: job `gateway-health-store-maintenance|23 * * * *|UTC|/api/v1/health/internal/maintenance`, created only for an environment where the store is enabled. `setup-health-store-alarms.sh`: CloudWatch metric filter on the maintenance log line, alarm when **no successful run for 4 h** (the job runs every hour: schedule `23 * * * *` instead of daily, ensure + purge are idempotent), a **daily partition check** (`health_store_partition_check`, run by the same job at 02:23 UTC, alarm if tomorrow's partition is missing in any tier), a metric filter on `health.store.partition_missing`, and alarms for the four placement triggers (Change 4) → SNS `vitana-alarms-prod`.

**A3 — account deletion reaches the raw bucket (vitana-v1)**

12. `_shared/erase-health-raw.ts` calls `POST /api/v1/health/internal/erase-raw` with the service credential the storage bridge client already uses; `request-account-deletion/index.ts` calls it after `erase_user_data` and, like the VTID-05053 storage step (F10), keeps the account (`storage_incomplete`) on an error or `residual > 0`. A `404 HEALTH_STORE_DISABLED` answer counts as "nothing to erase" (store never enabled). Account erasure therefore removes all tiers (via `erase_user_data`, including rows inside the 7-day suppression window) and the S3 batches at once.
