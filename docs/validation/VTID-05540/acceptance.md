# VTID-05540 acceptance (eng-gitlab-m2/rehearsal)
Change types: Tooling/docs, Integration.
Outcome: one command shows whether the whole path (agents, fleet, merge bot, `main`) works on a scratch project before any real repository depends on it: `node scripts/eng/rehearse.mjs --project rehearsal --agents 12` (what `m2.sh rehearse` runs on the GitLab machine) puts a seed on `main` through the bot, opens 5 control and 12 lane merge requests from the four seat accounts, plays the reviewer as `agent-reviewer`, waits for `bot-land`, and prints a report whose verdicts are the acceptance A1, A2, A3, A4 and A8 of plan §9. Exit 0 only when all five held.
States: the project is not marked `rehearsal`, is mirrored, has a webhook (file or live), or main is not the native profile: refuses to start, exit 2, nothing written. A job stuck: the report names it (job id, status, merge request). The fleet does not scale: the report shows the machine launches AWS refused with its message and fails A1. The bot does not land: the report lists each unlanded lane with every reason the bot gave. The seed does not land (25 minutes) or GitLab shows no push event for the reviewer's commit (2 minutes): the run stops there, opens nothing else, still prints the report. The role of the GitLab machine may not read the fleet group (either `autoscaling:DescribeAutoScalingGroups` or `autoscaling:DescribeScalingActivities` denied), or the built seed does not pass its own tests on this machine: refuses to start, exit 2, nothing written, naming both actions and the one denied, or the failing test. A read of the fleet group that fails during the run (a throttled call) is tried again at the next poll; if it never works A1 is NOT PROVEN with the error and the two actions, and the rest is decided.
Surfaces: the project `vitana/rehearsal` (four writes: commit, open and close a merge request, delete a branch) and the ASG `vitana-eng-fleet` (describe only). AWS: the seven token secrets `vitana/engineering/gitlab/agents/<username>`, read only, and the two Describe reads of the fleet group (once before the run, the group at every poll, the scaling activities once at the end, at most 500). Nothing else, nowhere else. Locales and accessibility: n/a (infra and tooling, no user-visible string).
Contract: plan §3.8 and the A1 to A4 and A8 definitions of §9. The report format is documented in the header of `scripts/eng/rehearse.mjs` and in `infra/gitlab-engineering/rehearsal/README.md`. Decisions taken inside the plan (for Gate 2):
- D1 (§3.8, §3.3). `main` of a native project takes no push, so the seed reaches `main` through a merge request of lane `rehearsal/seed`, reviewed by `agent-reviewer` and landed by the bot like any other. A current seed is left alone; an outdated file is updated through the same route.
- D2 (§9 A4). Five control merge requests besides the 12 lanes, one for each refusal the plan names. "No current review" is two controls (no review at all, and a review made stale by a later code change), because the bot gives different reasons.
- D3 (§3.4). The collab tooling is copied to `tools/collab/`, not `scripts/collab/`: `queue.mjs` and `protected-gate-files.json` are protected gate files and the bot would refuse the seed merge request.
- D4 (§3.4). The reviewer's and the builders' commits are made through the Commits API with their own tokens (no clone, no git credentials). The bot trusts a review commit found in a push event of `agent-reviewer`; the script proves that event exists after the first review and otherwise stops with the reason. Not verified against a real GitLab (see below).
- D5 (task statement). Exit 2 is also a refusal to start: it always means nothing was written. Exit 1 means the run started.
- D6 (§9 A1). Peak fleet size is the most machines in the ASG in any state, the largest of the samples (every 15 seconds), and the report also gives how many were booting or serving. "Each job on its own machine" is machines launched >= jobs run from the activity history, as §9 says.
- D7 (§9 A1; review finding 4). The second wave (the reviews) is pushed as soon as the first job of a first-wave merge request has started, or after 8 minutes. It no longer waits for every first-wave job: those jobs last seconds and their machines are deleted when they end, so the machines of the first wave could be gone before the second wave asked for its own, and the 20-machine overlap would have depended on timing. A job on a pipeline of `main` does not count. The plan's A1 numbers (20 machines, launched >= jobs, 0 within 900 s) are unchanged. The central CI cannot be changed by this lane.
- D8 (§9 A8). A8 is decided from facts the rehearsal can see (no job on the legacy runner, the settings check clean); "paused after A1" is the owner's step and is only noted.
- D9 (§3.8). All reads are made with `bot-land` (the one account with the rights to read hooks, mirrors and protection) through a client with no write method; every write is made with the account that owns it.
- D10 (§9 A1). With `--agents` below 12 only the 20-machine peak is skipped (and the report says so).
- D11 (§3.8). A negative control that fails prints FAIL and does not fail the job, so the rest of the rehearsal still runs and the report decides.
- D12 (§3.8). `gitlab-host` tries 22, 80, 443 and 8080; a missing address of the machine is a FAIL, never a quiet pass.
- D13 (§3.4). The run closes merge requests left open by an earlier run (branch `rehearsal/…`) and refuses if any other merge request is open, because the bot would land it.
- D14 (§9 A2; review finding 1). `imds` fails only when a token is issued or a tokenless read returns 2xx. The plan's wording "unreachable" is read as "yields no token and no data": with tokens required and hop limit 1, AWS answers a tokenless read with 401 and never delivers the answer to the token request, so counting any HTTP status as a failure would fail a correct fleet. The control still catches a hop limit of 2 (the token request is answered), IMDSv1 (the read returns data) and host networking.
- D15 (§3.8; review finding 2). Only a denial of one of the two reads is a refusal at the start; another failure of those reads is a note. A transient error must not block an hour-long run, and a denial can never be repaired by waiting. The dry run makes the same two reads, which is how the owner learns of a missing grant without starting anything.
- D16 (§3.4; review finding 5). The seed's self-test runs `node --test` on the seed's `test/**` with a clean environment, not `npm test` itself: that is the part of `npm test` that decides its exit code, it needs no `npm` on the machine, and it does not run the negative controls (which would probe the GitLab machine, not a job).
