## Decisions taken (inside the approved plan)

1. **Password injection:** the plan said "read by the runner from Secrets Manager and given to the sidecar at start"; F11 says the password lives only in the sidecar. Implemented the stricter reading: ECS injects it as a secret of the kiro-browser container only — the runner process never reads it (kiro-cli runs as the runner's user and could read its parent's memory/environment).
2. **Per-run cap authority:** the gateway counts `kiro.image` events per run (authoritative, works across gateway tasks); the sidecar asks `GET /quota` first so no page is opened past the cap. The relay never counts.
3. **Cross-task append without a migration:** inbox rows with negative `seq` in `kiro_run_events` instead of a new table.
4. **Registry token:** a dedicated secret (`browser-registry-token`) shared by the runner and the sidecar, not the runner token — a compromised Chromium could otherwise reach the runner's key API.
5. **Staging without provisioning:** the runner still deploys (with a `::warning`) when the sidecar's ECR repo/secret do not exist yet, instead of failing the runner deploy.
6. **Storage helper:** a small own helper on the existing `storage-provider.ts` (same bucket `operator-media`, path `kiro/<user>/<thread>/<uuid>.png`); to be folded into Phase 2's shared media helper when it lands.
7. **Image returned to Kiro:** the tool result carries media ids, sizes and signed URLs as text; image content blocks back to Kiro are left for when Phase 2 records `promptCapabilities.image`.

## Open — post-deploy (cannot be done from a session without AWS)

1. **Owner:** `scripts/aws/setup-kiro-runner-staging.sh provision --apply` (ECR `vitana/kiro-browser`, registry secret, execution-role read) and `set-browser-password --apply`. Until then staging deploys the runner without the sidecar (warning in the job).
2. **Fargate sandbox proof (first step of Phase 5):** the first staging roll prints `kiro-browser start: chromium … started (sandbox on)` or `chromium did not start with the sandbox: …` in the job summary. If it failed: re-dispatch `AWS-STAGE-DEPLOY-KIRO-RUNNER.yml` with `browser_no_sandbox=true` (fallback only inside the dedicated sidecar). Record the result and the image size (the CI build step writes `kiro-browser image size: N MiB`) in the PR.
3. **Bucket `operator-media`** is created by Phase 2's setup script; screenshots answer 502 "storage failed" until it exists.
4. **Console rendering** of `kiro.image` in the step list belongs to the Phase 2 console module (`kiro-console.js`); the events are recorded and replayed already.
5. Production stays off until the owner dispatches `AWS-PROD-DEPLOY-KIRO-RUNNER.yml` with `enable_browser=true` after setting `KIRO_BROWSER_PROD_REGISTRY_TOKEN_ARN` (and optionally `KIRO_BROWSER_PROD_PASSWORD_ARN`).
