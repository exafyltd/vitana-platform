## 3. Order before any broader autonomy activation

This section orders fixes. It does not recommend activating anything: every autonomy flag, control and level stays as
it is, and any change to them is owner stop 13 (platform `CLAUDE.md` NEVER 34, `CLAUDE.md:201`).

The critical risks must be fixed, and their verification evidence recorded, before any widening of autonomy (raising
the self-healing autonomy level, arming execution for more producers, enabling the Event Loop, or adding autonomous
producers):

1. **AR-07, worker claim fails open.** It is first because every other autonomous action depends on a single owner
   per VTID. Fix the route to fail closed, and put the predicate in `claim_vtid_task`.
2. **AR-01, exact-sensor verification.** Without it no autonomous fix can be shown to work, so AR-03 and AR-04 cannot
   be judged either. AR-02 (production default host) is fixed in the same change, because the verifier's host is part
   of the sensor contract.
3. **AR-03 and AR-04, rollback mechanism and event semantics, together.** A real AWS revert plus event types that
   say what happened. Fixing only the mechanism leaves `completed` events that mean "requested" in the history.
   AR-13 (metadata replace) goes in the same change because it is the same write.
4. **AR-06, Event Loop cursor.** This is critical only if the loop is to run. While `AUTOPILOT_LOOP_ENABLED` stays off it
   is fixed or the loop is retired before the flag is ever considered.

The high risks follow, in this order: AR-05 (fallback VTID), AR-12 (worker-runner existence; it also decides what AR-07's
end-to-end test runs against), AR-08 (tenant keys, sequenced by the multi-tenant programme), AR-09 (alert intake),
AR-10 (publish success at dispatch). AR-11 waits for the owner's decision and is not an autonomy fix.

Two defaults stay on today and are not changed by this register: `DEV_AUTOPILOT_EXECUTOR_ENABLED` and
`DEV_AUTOPILOT_WATCHERS_ENABLED` (`services/gateway/src/index.ts:2279,2293`). Their live values are Unknown. The
evidence needed is the read-only task-definition record named in §1.
