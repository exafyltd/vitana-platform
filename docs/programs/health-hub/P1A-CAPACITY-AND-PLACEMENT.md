# Health Hub store — capacity model and placement record (Phase 1 / A1)

VTID-05158 (Health Hub Phase 1 package A1; siblings A2 VTID-05159, A3 VTID-05160), program VTID-05020
(`docs/programs/health-hub/HEALTH-HUB-PLAN.md` §3.3, round-1 F7: "capacity model required in the Phase 1 plan").
Sparring record: `docs/validation/VTID-05158/plan-sparring.md` (Change 4).

## Decision

**Placement: Aurora — the production cluster and database, schema `public`, plain declarative partitioning.**
Store migration: `supabase/migrations/20261014100100_vtid_05158_health_store.sql` (APPLY TARGET: Aurora only — 0T first,
production after the cutover; never Supabase).

Reasons:
- Scenarios S and M are well inside one Postgres cluster when partitions are **dropped** rather than deleted (the
  5-minute tier is daily-partitioned and its partitions are dropped after 30 days).
- `erase_user_data()` and RLS already cover partitioned `public` tables (VTID-04765), so there is one erasure path, one
  access model, one backup/PITR and one DPIA surface. The Aurora-safe `erase_user_data()`
  (`20261014100000_vtid_05158_erase_user_data_aurora_safe.sql`) is part of A1 and a named go-live check.
- The gateway reaches Aurora through the existing PostgREST path; supabase-js code runs unchanged.
- No extension is assumed (no pg_partman, pg_cron or time-series extension): the same SQL runs in CI Postgres, 0T and
  production. Partition maintenance is `health_store_ensure_partitions` / `health_store_purge`, run hourly by the
  gateway maintenance job (A2); `health_store_partition_check` backs the daily "tomorrow's partition exists" alarm.

**Not chosen now:** a separate time-series store. It doubles erasure, access-control, backup and DPIA work for volumes
Postgres handles at S/M.

**Re-evaluation:** crossing any trigger below opens a new sparred plan comparing a dedicated Aurora cluster for the
store (same schema, smallest change) with a time-series engine.

**Backfill rate** is not a server-side constant. The aggregate backfill rate is governed by the native module's
throttling — Health Sync v1 batch size (≤ 1,000 records per batch) and sync interval/backoff — plus the store's
per-member quota (A2). The M wave figure assumes connects spread over 7 days. It is monitored against the
"> 1,000 upserts/s sustained" trigger, and a wave approaching it is slowed by Health Sync's server-driven backoff, not
by the store.

## Inputs

- 205 `auth.users` on 2026-08-25 (`docs/AURORA-B4-SIZING-REFRESH.md:18`); ~445 real members in the production tenant
  (CLAUDE.md rule 43, VTID-03990). Scenario S uses 450.
- Program success target: 40% of active members connected (`HEALTH-HUB-PLAN.md` §7).
- Device pre-aggregation (Health Sync v1, S1): series arrive as aligned 5-minute (≤ 30 days old) or hourly intervals,
  one item per interval; records are one item per OS object. There are no per-sample rows anywhere.

Notes on the figures:
- "Year-one total" is the steady 5-minute tier plus one year of lifetime-tier growth; each member's one-off backfill
  adds ≈ 2.8 MB to the lifetime tiers on top (S ≈ 0.5 GB, M ≈ 11 GB, L ≈ 113 GB).
- The sparred plan's table was rounded by hand. Where the script differs it is rounding only: M backfill wave 284/s
  (plan 285/s), S S3 ≈ 0.1 GB (plan ≈ 0.2 GB), year-one S ≈ 3.6 GB (plan ≈ 4 GB), backfill batches given as both the
  store's ≤ 5,000-item calls (9) and Health Sync's ≤ 1,000-record wire batches (43) (plan ≈ 10).
- Peak = 10 × average. The trigger line treats the modelled peak as if it were sustained, which is conservative.
