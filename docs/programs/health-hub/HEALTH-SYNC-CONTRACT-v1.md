## 1. Endpoints

| Method and path | Auth | What it does |
|---|---|---|
| `GET /api/v1/health/ingest/contract` | none | `{contract_version, supported_majors, max_minor, catalogue, limits, error_codes}`. Call it at app start; never send a field or a code it does not list. |
| `POST /api/v1/health/ingest` | member JWT | One batch (section 3). |
| `GET /api/v1/health/ingest/status?source_kind=&install_id=` | member JWT | Read-only: `source_state`, the member's consent per sync category on that source, `ingest_enabled`, `store:{enabled, reason}`, `store_pending`. |
| `POST /api/v1/health/ingest/source-state` | member JWT | `{source_kind, install_id, state:'os_permission_revoked'|'active', permitted_categories[]}`. Same gate as `POST /`. |

## 2. Device auth

- `Authorization: Bearer <Supabase access token>` of the signed-in member. supabase-js keeps the session (refresh token)
  in Keychain / Keystore through expo-secure-store; never in web storage.
- Background tasks refresh the session before sending. On `401` the app refreshes once and retries; a second `401`
  pauses sync until the next foreground session.
- `install_id`: a UUID the app generates once, keeps in secure storage and sends with every batch. It tells two phones
  of one member apart. It is not a credential.
- Identity comes only from the token. A batch has no user or tenant field; sending one is `400 INVALID_BATCH`.
- AI-assistant (OAuth client) tokens are refused (`403 DELEGATED_TOKEN_NOT_ALLOWED`). No service or staff path writes
  for a member.

## 3. Batch format

`Content-Type: application/json`, optionally `Content-Encoding: gzip` (recommended). At most 512 KB as sent and 4 MB
after decompression; at most 1,000 records and 1,000 deletions.

```json
{
  "contract_version": "1.0",
  "batch_id": "<uuid, generated by the app, the same on every retry of this batch>",
  "source": { "kind": "apple_health" | "health_connect", "install_id": "<uuid>", "platform": "ios" | "android",
              "os_version": "18.1", "app_version": "1.4.0", "device": { "manufacturer": "Apple", "model": "Watch7,1" } },
  "sync_mode": "incremental" | "backfill",
  "records":   [ { "record_id", "type", "value"?, "stats"?: {"n","sum","min","max"}, "unit", "start", "end", "tz",
                   "origin_app_id"?, "stages"? } ],
  "deletions": [ { "record_id", "type" } ]
}
```

- The schema is strict: an unknown field anywhere is `400 INVALID_BATCH` with `details:[{path, code:'unknown_field'}]`.
- `apple_health` goes with `ios`, `health_connect` with `android`.
- `start`/`end`: ISO-8601 with an offset (`Z` or `±hh:mm`). `tz`: the IANA zone of the measurement.
- `unit` must equal the catalogue unit (UCUM). The app converts; the server never does (`UNIT_MISMATCH`).
- `stages` (sleep_session only): `[{stage: awake|light|deep|rem|asleep|in_bed|out_of_bed, start, end}]`, at most 200.

### 3.1 Series codes: pre-aggregate on the device

`series_sum` and `series_stats` codes (steps, active energy, exercise minutes, distance, heart rate) are never sent per
sample. The app aggregates on the device (HealthKit statistics collection query / Health Connect aggregate by duration)
into **aligned UTC intervals**: 5 minutes when `start` is within the last 30 days, 1 hour when older.

- One item per interval, `record_id = "<type>:<start as ISO-8601 UTC>"`, e.g. `steps:2026-10-13T08:00:00.000Z`.
- `series_sum`: `value` = the interval sum. `series_stats`: `stats:{n, sum, min, max}` and no `value`.
- A changed interval is re-sent whole (answer: `updated`). An interval whose samples are all gone is sent as a
  deletion of that `record_id`.

### 3.2 Record codes

Sleep sessions, workouts, weight, body fat and spot values: one item per OS object; `record_id` = the HKObject UUID /
the Health Connect `metadata.id`.

## 4. Data catalogue v1 (closed)

Units, kinds and plausibility ranges come from the health store catalogue; `GET /contract` publishes them.

| Category (consent key) | Type | HealthKit | Health Connect |
|---|---|---|---|
| activity (`sync_activity`) | `steps` | HKQuantityTypeIdentifierStepCount | StepsRecord |
| | `active_energy` | HKQuantityTypeIdentifierActiveEnergyBurned | ActiveCaloriesBurnedRecord |
| | `exercise_minutes` | HKQuantityTypeIdentifierAppleExerciseTime | ExerciseSessionRecord (EXERCISE_DURATION_TOTAL) |
| | `distance` | HKQuantityTypeIdentifierDistanceWalkingRunning | DistanceRecord |
| | `workout` | HKWorkoutType | ExerciseSessionRecord |
| sleep (`sync_sleep`) | `sleep_session` (+ `stages`) | HKCategoryTypeIdentifierSleepAnalysis | SleepSessionRecord |
| heart (`sync_heart`) | `heart_rate` | HKQuantityTypeIdentifierHeartRate | HeartRateRecord |
| | `resting_heart_rate` | HKQuantityTypeIdentifierRestingHeartRate | RestingHeartRateRecord |
| | `hrv_sdnn` | HKQuantityTypeIdentifierHeartRateVariabilitySDNN | — |
| | `hrv_rmssd` | — | HeartRateVariabilityRmssdRecord |
| body (`sync_body`) | `body_weight` | HKQuantityTypeIdentifierBodyMass | WeightRecord |
| | `body_fat_percentage` | HKQuantityTypeIdentifierBodyFatPercentage | BodyFatRecord |

Anything else is `UNSUPPORTED_TYPE`. **Blood glucose / CGM, reproductive and clinical records are excluded** (program
§2, owner decision 7): the app must not request OS permission for them.

## 5. Consent (fail closed)

- Consent is per data category × source: `sync_<category>` with the resource `apple_health` or `health_connect`.
  Apple Health sleep and Health Connect sleep are two consents.
- Order in the app: the member grants the Vitana consent first (`POST /api/v1/health/consents/grant`,
  `granted_via: "native_health_sync"`), then the app asks for the OS permission. Withdrawal works on the web too
  (Settings › Privacy).
- The server checks each category present in a batch once. A record of an unconsented category is answered
  `CATEGORY_NOT_CONSENTED` and is **dropped before it reaches the store**: it is never stored, archived or quarantined.
  When it happens the app purges its queued records of that category and stops reading it.
- No consented category in the batch and no deletion: `403 CONSENT_REQUIRED` with `categories:[...]`.
- **Deletions are always processed**, whatever the consent state.

## 6. Idempotency and sync

- Batch: `(member, batch_id)`. Re-sending the same batch (same content) returns the first outcome with `replay:true`
  and writes nothing again. The same `batch_id` with different content is `409 BATCH_ID_REUSED`; send a new `batch_id`.
- Record: `(source, record_id)`. A resend is `duplicate`; a changed value is `updated`.
- Anchors and change tokens stay on the device; the server keeps no cursor. The app advances its anchor after a `200`,
  whatever the per-record outcomes. Per-record codes are not retryable, with one exception: `STORE_UNAVAILABLE`
  (`retryable:true`) means the store could not take that record; re-send it in a **new** batch.
- Backfill: 90 days by default. `start` older than 400 days or `end` more than 5 minutes in the future is
  `OUT_OF_WINDOW`.
- OS permission revoked: `POST /source-state` with `os_permission_revoked` pauses the source; while paused every batch
  is `409 SOURCE_PAUSED`. `active` resumes a source paused that way. A source the member disconnected on the web is not
  resumed by the app (`changed:false`, `source_state:"disconnected"`); batches for it answer `409 SOURCE_PAUSED`.

## 7. Responses

`200`:

```json
{ "ok": true, "batch_id": "…", "replay": false,
  "counts": { "stored": 1, "duplicate": 0, "updated": 0, "deleted": 0, "rejected": 1 },
  "rejected": [ { "record_id": "…", "code": "CATEGORY_NOT_CONSENTED" } ],
  "consent": { "activity": "granted", "sleep": "not_granted" },
  "source_state": "connected" }
```

`deleted` counts deletions of records that no longer exist as well (a deletion is idempotent).

Per-record codes: `UNSUPPORTED_TYPE`, `UNIT_MISMATCH`, `IMPLAUSIBLE_VALUE`, `OUT_OF_WINDOW`, `CATEGORY_NOT_CONSENTED`,
`INVALID_RECORD`, `STORE_UNAVAILABLE` (retryable, see section 6).

Batch errors: `{ok:false, error, retryable, retry_after_s?, details?}`. Never a database or vendor message.

| Code | Status | Retryable |
|---|---|---|
| `INVALID_BATCH` | 400 | no |
| `UNSUPPORTED_CONTRACT_VERSION` | 400 | no; `details.supported_majors` |
| `UNAUTHENTICATED` | 401 | refresh once, then retry |
| `TENANT_REQUIRED` | 400 | no |
| `CONSENT_REQUIRED` | 403 | no |
| `SOURCE_PAUSED` | 409 | no; stop until the member re-enables |
| `INGEST_DISABLED` | 409 | no |
| `BATCH_ID_REUSED` | 409 | no; new `batch_id` |
| `BATCH_TOO_LARGE` | 413 | no; split the batch |
| `UNSUPPORTED_ENCODING` | 415 | no |
| `RATE_LIMITED` | 429 | yes, after `Retry-After` |
| `STORE_PENDING` | 503 | yes, with back-off |
| `STORE_UNAVAILABLE` | 503 | yes |

`401`, `400 TENANT_REQUIRED`, `403 TENANT_NOT_MEMBER` and `503 TENANT_CHECK_UNAVAILABLE` come from the gateway's shared
auth middleware and carry `{ok:false, error, message}`; act on the status and `error`. `/status` and `/source-state`
answer `400 INVALID_REQUEST` for a malformed query or body.

Rate limits (defaults, per gateway task, so approximate): a per-IP backstop before auth, then 120 batches per member per
hour and 10 concurrent batches per member.

## 8. Versioning

- `contract_version` is `major.minor`. The server accepts major 1 with any minor up to `max_minor` from
  `GET /contract`.
- A minor version only adds optional fields or catalogue codes, and the server ships it first. Because the schema is
  strict, the app never sends a field or code newer than `GET /contract` reports.
- A new major is a new schema served next to the old one until adoption passes the threshold. The minimum app version is
  enforced by the native program's `GET /api/v1/app-config`, not here.
- The JSON Schema lock makes every change explicit: a changed schema without a version bump fails CI.

## 9. Aggregators (Phase 2)

An aggregator adapter (`AggregatorBatchAdapter`, `services/health-sync/adapter.ts`) maps a verified webhook's normalised
events into one v1 batch and calls the same adapter with `channel:'aggregator'`. Consent is `sync_<category>` with the
aggregator's connector id as the resource. The vendor is chosen in Phase 2; the legacy Terra/Vital webhook path is
consent-gated by D10 WP3 and rerouted onto this adapter in Phase 2.
