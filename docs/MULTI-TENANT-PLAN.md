## 1. Goal and success criteria
**Two scopes everywhere it matters.** *Community* = the member's own tenant (its feed, groups, events, moderation, branding, tenant-only offerings); *Network* = the whole Vitanaland member base across tenants, entered deliberately through the same mode switch on messenger, Discover and matching. Isolation work in this plan protects the Community scope and everything private; the Network scope is an explicit, opt-in, reduced-data layer — not a leak.
The product every tenant gets is now: the community web app **plus native iOS/Android apps with health data (Apple Health, Health Connect, cloud wearables, labs) and commerce/Discover built in.** Multi-tenancy must hold across all three: one native app serves every tenant, a member's health data is theirs (never the tenant operator's), and Discover/commerce eligibility is evaluated per tenant.
A new tenant (first: Alkalma or a named new community) gets the full Maxina product — same roles, same screens, the same role-separated Vitana assistant, its own landing/intro, branding, content and community — provisioned without hand-written SQL, isolated from other tenants, and **with Maxina's behaviour unchanged** (golden-tested).
Principle: **mirror the platform, not the content.** Maxina becomes "tenant #1 with a content pack", not the template.
Exit criteria at M2: 5 invited pilot users complete signup → onboarding → ORB in the new tenant; zero cross-tenant reads in the isolation suite (local stack + CI) and `ci_tenant_isolation_health()` reports zero foreign-tenant mismatches in production; Maxina golden suite unchanged; no Maxina/Mariia string in the new tenant's surfaces.

## 4. Target architecture
1. **Resolution chain (one implementation):** host (`tenant_domains.host`) → path `/:slug` → JWT claim `tenant_id` → primary `user_tenants` row. Unresolved → reject (no oldest-tenant, no …0001). Anonymous → public RPC `resolve_tenant(host, slug)`. Host tenant ≠ member → "join this community" flow, never silent fallback.
2. **Tenant context in tokens — one claim, one source of truth:** a Supabase **Custom Access Token Hook** reads the user's active `user_tenants` membership (validating `app_metadata.active_tenant_id` as a *preference* only — never trusted) and emits top-level `tenant_id` + `tenant_role`. That claim becomes the ONLY tenant source: `current_tenant_id()` (works unchanged), `caller_tenant_id()` (folded in), gateway `TenantContext` (replacing the `app_metadata.active_tenant_id` read at `auth-supabase-jwt.ts:273` and the `limit(1)` fallback at `:510-520` → `resolvePrimaryTenant()`), and edge functions. **The hook is a project-wide production auth change** (one Supabase project): it must fail open (`EXCEPTION WHEN OTHERS` → return original claims; single indexed lookup; short statement timeout), ships as a migration plus a recorded auth-config step that the owner approves and applies, with a one-step disable runbook and a login p95/error check immediately after enabling. Rollout: (a) hook emits `tenant_id_shadow` only; mismatches vs membership are logged to a table as decisions (not heartbeats) for 7 days; (b) only after S-E is fixed and policies are classified (step 3) does it emit `tenant_id`. Token staleness (claims fixed until refresh ≈1 h, realtime sockets keep old tokens): tenant-shared policies also check membership via an `is_member(tenant_id)` helper, and removing a membership revokes the user's sessions. **Ordering gate (N3):** `current_tenant_id()` is NOT changed in place. The new resolver ships under a separate name, `tenant_id_for_policies()`, used only by policies already classified (§4.3); bare policies are rewritten table by table to `user_id = auth.uid() AND tenant_id = (select tenant_id_for_policies())` (user-private) or `(select is_member(tenant_id))` (tenant-shared) before switching. A WS0 DB-lint hard gate counts bare policies (`current_tenant_id()` without `auth.uid()`/`current_user_id()`/`is_member`/`is_tenant_admin`, outside an owner-tagged tenant-shared allowlist) and must read ZERO, checked read-only against live before the final migration that redefines `current_tenant_id()` as an alias of the new function; pgTAP asserts a_member cannot read a_admin's user-private rows on every one of the 18 tables (and the health tables). **Degraded path (N2):** once policies depend on the claim, a disabled or failing hook must not lock members out. The new resolver is `coalesce(<claim tenant_id, if is_member>, <auth.uid()'s primary user_tenants row>)` — a STABLE SECURITY DEFINER function over the unique `(tenant_id, user_id)` index, never reading `app_metadata`; `is_member()` and this fallback share one lookup, and policies call them through `(select current_tenant_id())` so Postgres evaluates them once per statement (initPlan), not per row — keeping cost bounded on `user_notifications`/`chat_messages`. The gateway keeps `resolvePrimaryTenant()` as the same documented fallback. Two runbooks: disable during shadow (no effect on access) and disable after live (access continues via the membership fallback; only multi-tenant switching degrades). A local-stack test runs with the hook OFF after the policy rewrite and asserts members still see their own rows and nothing of the other tenant.
3. **Database:** every policy classified user-private (`user_id = auth.uid() AND tenant_id = current_tenant_id()`), tenant-shared, or admin-only (`is_tenant_admin(tenant_id)`); RLS mandatory on browser/realtime-reachable tables; `tenant_id NOT NULL` + FK on tenant tables; service-role-only tables get NOT NULL + gateway wrapper rather than client RLS.
4. **Gateway:** middleware builds `req.tenant: TenantContext { tenantId, slug, role, source, settings }` (settings cached 60s); data access to tenant tables through `tenantDb(ctx)` (service-role wrapper injecting tenant predicates for a schema-derived `TENANT_TABLES` list; raw access only in allowlisted platform/cron code); headers never set tenant except for exafy_admin/service callers; jobs iterate `tenants WHERE is_active` and build a context per tenant.
5. **Config = packs; config inherits, instance data is copied.** Layers: code default ← platform DB default ← tenant override. **NEVER rule 41 applies:** packs supply FACTS (community name, anchor person, story, offer, tone) and English INTENTS to the assistant — spoken wording stays model-composed; `{{brand}}` string templating is used only for UI strings, push, email and `tt()` catalog entries, never for a sentence Vitana speaks. Brand pack (`tenants` + `tenant_settings.brand`: name, tokens, legal entity, support/sender, domains, app ids; assets in Storage `tenant-assets/<slug>/`), content pack (repo i18n with `{{brand}}` + `tenant_content_overrides(tenant_id, locale, key, value)`), persona pack (`ai_personality_config` + existing `tenant_assistant_config` via `getEffectiveConfig`; KB baseline + `knowledge_docs.tenant_id` overlay), feature pack (`tenant_settings.feature_flags`; no per-tenant navigation in this program). Persona splits into a fixed Vitana identity block (name, pronunciation, safety, role separation) and a tenant block (community, anchor person, story, offer, tone). Brand hierarchy: "<Community> on Vitanaland, with Vitana".
6. **Provisioning:** idempotent `provision_tenant(slug, name, host?, admin_email)` writes only instance data (tenant row, tenant_settings incl. Jev flag/budget, AI provider policies, notification type controls, system chat groups + bot, autopilot settings/bindings, tip cursor, founding campaign row, backfill/job enrolment, ERP bootstrap request, first-admin invitation). It never copies config/content. `GET /admin/tenants/:id/readiness` reports domain, assets, legal links, sender, first admin, isolation smoke.
7. **Migrations — every DB change is live in production on apply** (one Supabase project; flags cannot make a migration, trigger, policy or hook dark). Each slice is split into a CODE part (merged dark behind flags) and a DB part with: dry-run on the D11 local stack, pre-approved rollback migration, off-peak window, explicit owner approval to apply, and a post-apply read-only verification query. Rollback after a data move: the `bak_*` snapshot table is retained 30 days and the rollback migration restores from it. Pattern: expand/contract only — nullable column → BEFORE INSERT trigger filling tenant from the actor's resolved tenant → batched backfill (1–5k rows/txn, off-peak, realtime fan-out considered) → `CHECK … NOT VALID` → `VALIDATE` → `SET NOT NULL`; `lock_timeout` + retries; snapshot tables before data moves; read-path filters behind per-tenant flags; rollback migration pre-approved.

Until the claim matches, the app fetches no tenant data. Non-member → "join this community" screen; unresolved → community picker; never a silent Maxina default. This minimal, non-UI switch mechanism is pulled forward into N1 (the full switching UI stays deferred). Path slugs need a reserved list derived from the registry (`screens.json` top-level routes) and enforced by `provision_tenant`. Custom domains (M3+) require associated-domain entitlements compiled into the binary, i.e. an app release per domain. App-level branding (store name, icon, splash) is the platform brand (D16); tenant branding is applied in-app from the brand pack after resolution. Push goes direct APNs/FCM from the gateway. `user_device_tokens` today keeps one row per (user, token) whose `tenant_id` is overwritten on each registration (`routes/notifications.ts:72-78`) while delivery filters by the notification's tenant (`notification-service-repository.ts:28-34`) — a dual member silently loses the other tenant's pushes. The native shell must ship tenant-aware from its first build — no Maxina constants in `capacitor.config`, native strings, Info.plist usage texts or store metadata, except immutable store identifiers (bundle id `com.exafy.maxina`, AASA appID) if D16 reuses the existing listing. **Delivery model (D19):** default = the SPA build bundled into the app plus a governed over-the-air web-bundle channel; a store binary release becomes its own governed workflow (native build → TestFlight/Play internal → device verification on the local stack → owner approval → store submission), and the OTA channel is promoted only by PUBLISH so native users follow the same staging-first rule as web. **OTA compatibility gate:** every OTA bundle declares `min_native_version` (and required plugin versions) in its manifest; the native shell reports its version and installed plugins at startup (Capacitor App/Device info) and on device registration; the client refuses an incompatible bundle and stays on its last compatible one; native-dependent features (HealthKit, Health Connect, native push, transport flag) are gated by runtime capability detection, not by bundle version; OTA promotion checks the installed-binary distribution reported by devices; tested with an old-binary fixture. Consequences carried into WS7/WS9: the app origin (`capacitor://localhost` / `https://localhost`) added to CORS and the Supabase redirect allowlist; OAuth (Google/Apple, Commerce) runs in the system browser and returns via universal link; host-based resolution does not apply in-app. **Payments (D22):** digital goods/subscriptions/VTNA credits sold inside the native app fall under App Store 3.1.1 / Play billing; physical goods and real-world services (Discover, labs, events) may use Stripe.

## 8. Delivery model

Health and commerce migration volume (~15–20) is added to the estimate. Hot files (`orb-live.ts`, `app.js`, gateway `index.ts`, `App.tsx`): ≤20-line changes in their own PR, rebased just before merge.
- One VTID per slice of 2–4 PRs (~39 VTIDs to M2, ~67 in total — see §9), each sparred per VTID-04868; owner review in two fixed windows/day.
- Every merged CODE change is dark by default (env master `MT_RESOLUTION_V2` + `tenant_settings.feature_flags.mt.*`), because PUBLISH promotes the whole staging build. Flags gate gateway/frontend reads only — DB changes follow the §4.7 DB-slice protocol.
- Handoff: `docs/multitenancy/PLAN.md`, `DECISIONS.md`, `LANE-<A|B|C>.md` in vitana-platform; each session reads them, runs required suites, spars its slice, works on `mt/<lane>/<vtid>`, updates the lane doc.
- No test writes or sign-in probes against production; production verification is read-only SQL/RPC health checks and unauthenticated health/build-info GETs only (rule 48).
